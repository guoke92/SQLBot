# LangGraph 拓扑配置化 + 现网/目标两套配置

## 目标（已确认）

1. **拓扑配置化**：YAML 只描述 `nodes / edges / routers`；节点与路由函数仍是 Python，用 **dotted path** 解析。
2. **正式 key**：一般对话 registry key 为 **`chat`**（替换 `nlq`）；`analysis` 不再作为长期独立 product key（见迁移）。
3. **同时交付**：
   - **现网等价**配置（行为与今天 5 张图一致，便于先迁加载器）
   - **目标架构**配置（`chat` 单图内 `nlq_path` + `dialogue_path`；`config` 不变）
4. 治理：禁止补丁式双实现/长期兼容层；Core 仍无业务逻辑；`submit_graph` 仍是唯一入口。

---

## 设计原则

| 项 | 决定 |
|----|------|
| 配置表达什么 | 拓扑 + 解析目标（callable path、state 类型） |
| 配置不表达什么 | prompt 正文、SQL、业务 if/else、SSE 字段拼装 |
| 路由函数 | 具名 Python callable（禁止 YAML 内嵌匿名 lambda） |
| 预设路由 | 支持 `ok_or_fail` 工厂：`router: { type: ok_or_fail, next: build_context }` |
| END | 边目标用字面量 `END`；若 router 返回 `__end__`，path_map 可写 `__end__: END` |
| 单 builder | Core 只保留一个配置驱动 builder：`build_from_spec(graph_key)`，不再每个文件手写 `add_node` 链 |
| 真相源 | YAML 是拓扑真相源；Python 模块只保留 **nodes + routers + State TypedDict** |

## YAML Schema（统一）

```yaml
version: 1
graph_key: chat                 # 必须与文件名/注册 key 一致
state: apps.chat.graphs.chat_state.ChatState
description: "..."

nodes:
  prepare_record: apps.chat.graphs.chat_nodes.prepare_record_node
  fail: apps.chat.graphs.chat_nodes.fail_node
  # ...

edges:
  # 普通边
  - from: START
    to: prepare_record
  - from: early_finish
    to: END
  - from: fail
    to: END

  # 条件边
  - from: prepare_record
    router:
      type: ok_or_fail          # 内置工厂
      next: ensure_datasource
    paths:
      ensure_datasource: ensure_datasource
      fail: fail

  - from: generate_sql
    router: apps.chat.graphs.chat_routers.route_after_sql
    paths:
      early_finish: early_finish
      execute: execute
      fail: fail
```

**校验规则（loader）：**

- 所有 `nodes` 值可 import + callable  
- `edges.from/to` 引用的节点存在，或为 `START`/`END`  
- conditional 的 `paths` values ⊆ nodes∪{END}  
- `ok_or_fail` 的 `next` 必须在 `paths`  
- 禁止同一个 `graph_key` 双文件注册

## A. 现网等价配置（`graphs/current/`）

### A1. `chat.yaml`（现 `nlq` 拓扑；key=`chat`）

节点与现 `build_nlq_graph` 一一对应：

```
START → prepare_record
  ─ok_or_fail→ ensure_datasource
  ─ok→ match_terminology → match_training → match_custom_prompts
  → build_context → generate_sql
       ├ early_finish → END
       ├ execute
       │    ├ data_finish → END
       │    └ generate_chart → complete ─__end__→ END
       └ fail → END
```

- `state`: 迁移后的 `NlqState` 模块路径（可暂名 `ChatNlqState` 与现字段兼容）  
- routers: `route_after_sql` / `route_after_execute` / `route_after_chart` / `route_after_complete` + `ok_or_fail`  

### A2. `analysis.yaml` / `predict.yaml` / `recommend.yaml` / `config.yaml`

与现图边表一致（已从代码抽出）。predict 里原先的 **匿名 lambda** 改为具名：

```python
def route_after_success(state) -> Literal["complete", "fail"]:
    return "fail" if state.get("error") else "complete"
```

### A3. API 改 key（与配置同步，无别名层）

| 现状 | 修改后 |
|------|--------|
| `submit_graph("nlq", …)` | `submit_graph("chat", …)` |
| `register_graph("nlq", …)` | **删除**；由 loader 注册 `chat` |
| 静态测试扫 `nlq.py` register | 改为扫 YAML / `list_graphs()` |

`analysis` / `predict` 在 **current** 阶段仍独立 yaml + key（行为零回归）。  
目标阶段再删 `analysis` key（见 C）。

## B. Core：配置动态加载（唯一装配路径）

### `graph_loader.py` 职责

```
load_specs(dir) 
  → for each *.yaml: parse → GraphSpec.validate()
  → resolve_callable(dotted)
  → build_state_graph(spec) → compile()
  → register_graph(spec.graph_key, builder_closure)
```

`builder_closure(ctx, **kwargs)`：忽略业务 ctx（与现一致），返回 **已 compile** 或每次 `compile()`（保持与现 `build_*` 相同：每次 submit 调 builder）。  
推荐：**builder 内每次按 spec 新建 StateGraph 并 compile**（与今天一致，无全局 compiled 单例状态问题）。

### Bootstrap

替换：

```python
import apps.chat.graphs
import apps.config_assistant
```

为：

```python
from apps.conversation.graph_loader import bootstrap_graphs
bootstrap_graphs()  # 读 GRAPH_SPEC_DIR / default current
```

位置：`apps/api.py` + 测试 fixture；**去掉**模块 import side-effect `register_graph(...)`。

### 不做

- 热重载生产默认关闭（可 test-only `reload_graphs`）  
- YAML 里写 Python 源码  
- 第二套手写 `build_nlq_graph` 与 YAML 并存

## C. 目标配置（`graphs/target/chat.yaml`）

与已拍板架构一致：**仅两张主对话图 `chat` + `config`**。

```
START
  → prepare_turn
  → hydrate_working_set
  → ensure_datasource          # dialogue 也需 ds 时同一节点；可按 intent 跳过留到二期
  → route_turn
       ├ nlq_new | regenerate | repair_confirm → (nlq_path chain)
       └ explain_* | critique | clarify | repair_request → (dialogue_path chain)
  → finalize_turn → END
  fail → END
```

**nlq_path 节点**（复用现 nlq 节点函数，rename 前缀可选）：  
`match_* → build_context → generate_sql → execute → data_finish|generate_chart → …`

**dialogue_path 节点**（新模块；首版可 stub 语义但必须 **真实 callable 可 compile**）：

| 节点 | 首版行为（拓扑可跑） |
|------|----------------------|
| `dlg_resolve_anchor` | 校验 anchor；失败 set error |
| `dlg_load_evidence` | 装 evidence 到 state |
| `dlg_reason` | placeholder 或最小 LLM |
| `dlg_synthesize` | 流式/或固定文案 + 写 diagnosis 结构 |
| `dlg_maybe_repair_brief` | no-op 或写 pending brief |
| `dlg_complete` | 收尾 |

**注意：** 本任务用户选的是 **拓扑配置化**，不是「dialogue 产品能力一次做完」。  
因此 **默认运行 `graphs/current`**；`target/` 作为已校验可 `compile` 的架构稿。  
Cutover 到 target 另用明确开关/换 `GRAPH_SPEC_DIR`，**不** `chat`/`nlq` 双注册。

`target/config.yaml`：与 current 相同。  
`target` **无** `analysis.yaml`：文档写明 API `analysis` → `submit_graph("chat", forced_intent=explain_result, anchor=…)`（该 API 改造可列为紧随 PR，或同 PR 末段若风险可控）。

**predict：** target 说明“二阶段并入 chat.predict_path”；current 仍独立，避免 scope 爆炸。

## G. 风险与边界

| 风险 | 处理 |
|------|------|
| 循环 import（loader↔nodes） | nodes 不 import loader；loader 只 importlib 字符串 |
| LangGraph 节点名 = state key | 沿用现网已避让规则（config 的 `bound_tools`）；loader 可可选校验 |
| 一次改 API key 影响 MCP/前端 | 后端 graph_key 对外多不透出；扫 MCP `submit_graph` |
| target 未实现对话能力被误开 | 默认 `GRAPH_SPEC_DIR=current`；README 标明 |
| 长期 nlq 别名 | **不做**（已确认正式 chat） |
