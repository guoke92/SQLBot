# Agentic Batch Loop — 并发查询 + 渐进式流式展示

## 核心架构

一次用户问题 → LLM 规划多条 SQL → **并发执行** → 批量生成图表 → LLM 决定继续/总结/结束。
最多 3 轮迭代，每轮并发最多 5 条 SQL。

**并发安全关键发现**：`LLMService` 不是线程安全的（`generate_sql` 和 `generate_chart` 都会修改实例的 `sql_message`、`current_logs` 等可变状态）。因此：
- **SQL 规划**（generate_queries_node）：1 次 LLM 调用，返回多条 SQL — 无需并发
- **SQL 执行**（execute_queries_node）：**并发执行**，每条查询用独立 session + 独立 ChatLog — 共享 LLM 连接但不共享 LLMService 状态
- **图表生成**（generate_charts_node）：1 次 LLM 调用，返回多条图表配置 — 无需并发
- **决策**（decide_next_node）：1 次 LLM 调用

连接池限制：PG_POOL_SIZE=20 + MAX_OVERFLOW=30 = 50 连接上限。每条并行 SQL 持有 1 个连接，batch_size ≤ 5 安全。

### 1.2 节点实现（替换旧节点，保留底层 steps 函数）

**保留不变的节点**：`prepare_record_node`, `ensure_datasource_node`, `match_*_node`, `build_context_node`, `fail_node`

**删除旧节点**：`generate_sql_node`, `execute_node`, `generate_chart_node`, `data_finish_node`, `early_finish_node`

**新增节点**：

#### generate_queries_node
- 调用 `generate_sql(llm_service, session)` 获取 LLM 流式响应
- 解析 LLM 返回的 JSON 数组（多条 SQL）或单条 JSON（向后兼容 prompt）
- 每条 SQL 流式输出 `step-N-sql-result` 事件
- 将解析后的 plans 存入 `batch_plans`

**Prompt 改造**：在 `build_user_prompt` 中追加指导，告知 LLM 可以返回多条 SQL。
LLM 返回格式：
```json
[
  {"sql":"SELECT ...","tables":["t1"],"chart-type":"column","brief":"标题1"},
  {"sql":"SELECT ...","tables":["t2"],"chart-type":"pie","brief":"标题2"}
]
```
兼容单条：`{"sql":"SELECT ...","tables":["t1"],"chart-type":"column","brief":"标题"}`

#### execute_queries_node（并发核心）
```python
def execute_queries_node(state: NlqState) -> NlqState:
    plans = state["batch_plans"]
    results = [None] * len(plans)
    sink = StreamSink.from_state(state)
    llm_service = state["llm_service"]

    def _execute_single(idx: int, plan: dict) -> dict:
        """每条查询独立 session，不共享 LLMService 的可变状态"""
        with session_scope() as session:
            # 复用 protocol.execute，不调用 generate_sql（避免修改 llm_service）
            query_result = llm_service.protocol.execute(
                llm_service.ds, _plan_from_dict(plan)
            )
            result = query_result.as_dict()
            # 保存到 DB
            _save_step_data(session, llm_service.record.id, idx, result)
            return {"index": idx, "result": result, "plan": plan}

    with ThreadPoolExecutor(max_workers=min(len(plans), 5)) as pool:
        futures = {pool.submit(_execute_single, i, p): i for i, p in enumerate(plans)}
        for future in as_completed(futures):
            idx = futures[future]
            try:
                result = future.result()
                results[idx] = result
                sink.event({"type": "step-data", "index": idx})
            except Exception as e:
                results[idx] = {"index": idx, "error": str(e)}
                sink.event({"type": "step-error", "index": idx, "error": str(e)})

    return {**state, "batch_results": [r for r in results if r is not None]}
```

**关键**：`_execute_single` 使用独立 `session_scope()`（scoped_session 线程安全），不修改 `llm_service` 的可变状态。

#### generate_charts_node
- 1 次 LLM 调用，传入所有 batch_results 的样本数据
- LLM 返回多条图表配置（JSON 数组）
- 每条图表流式输出 `step-N-chart-result` 事件

#### decide_next_node
- 1 次 LLM 调用，传入 `all_steps` 的摘要
- LLM 返回：`{"action":"continue"}` / `{"action":"summarize","text":"..."}` / `{"action":"finish"}`
- 设置 `state["decision"]`

#### summarize_node
- 如果 decide_next 返回 "summarize"，将文本存入 `analysis_text`
- 流式输出 `analysis` 事件

#### complete_node 改造
- 将 `all_steps` 序列化存入 `ChatRecord.data`（JSON 数组格式）
- 将 `analysis_text` 存入新增字段
- 输出 `finish` 事件

### 1.3 路由

```python
def route_after_decision(state: NlqState) -> str:
    if state.get("error"):
        return "fail"
    step_index = state.get("step_index", 0)
    max_steps = state.get("max_steps", 3)
    decision = state.get("decision", "finish")
    if step_index >= max_steps:
        return "complete"
    if decision == "continue":
        return "generate_queries"
    if decision == "summarize":
        return "summarize"
    return "complete"
```

### 2.2 SSE 事件处理

```typescript
const steps = ref<StepResult[]>([])
const analysisText = ref('')
const reasoningSteps = ref('')  // 累积所有推理文本

onEvent((data) => {
  switch (data.type) {
    case 'batch-start':
      // 标记新批次开始
      break
    case 'step-sql-result':
      if (!steps.value[data.index]) {
        steps.value[data.index] = { loading: true, sqlAnswer: '', sql: '', chart: null, data: null, error: null, brief: '' }
      }
      steps.value[data.index].sqlAnswer += data.content
      reasoningSteps.value += data.content
      break
    case 'step-sql':
      steps.value[data.index].sql = data.content
      break
    case 'step-data':
      fetchStepData(recordId, data.index)
      break
    case 'step-error':
      steps.value[data.index].loading = false
      steps.value[data.index].error = data.error
      break
    case 'step-chart-result':
      steps.value[data.index].chartAnswer = (steps.value[data.index].chartAnswer || '') + data.content
      break
    case 'step-chart':
      steps.value[data.index].chart = JSON.parse(data.content)
      steps.value[data.index].loading = false
      break
    case 'analysis':
      analysisText.value += data.content
      break
    case 'finish':
      emit('finish', recordId)
      break
  }
})

async function fetchStepData(recordId: number, stepIndex: number) {
  const data = await chatApi.getChartData(recordId)
  // data.steps[stepIndex] 包含该步骤的结果
  steps.value[stepIndex].data = data.steps[stepIndex]?.data || data
}
```

### 2.3 index.vue 路由

普通对话统一使用 MultiStepAnswer。根据后端是否发送 `batch-start` 事件判断是单次还是多次查询。
如果后端只返回单条 SQL（LLM 认为一次就够），前端自动退化为单图表展示，无需特殊处理。

## 六、风险与对策

| 风险 | 对策 |
|------|------|
| LLMService 非线程安全 | 并发执行只用独立 session + protocol.execute，不修改 LLMService 状态 |
| 连接池耗尽 | max_workers=min(batch_size, 5)，PG_POOL_SIZE=20 足够 |
| LLM 返回格式不规范 | 降级为单条 SQL（兼容单对象和数组格式） |
| 多次 LLM 调用延迟 | 每批次流式输出，用户实时看到进展 |
| decide_next 死循环 | max_steps=3 硬限制 |
| 目标数据源连接池 | 并发数 ≤ 5，大多数数据源可承受 |
| 单条 SQL 场景退化 | LLM 返回单元素数组时自动退化为单图表展示 |
