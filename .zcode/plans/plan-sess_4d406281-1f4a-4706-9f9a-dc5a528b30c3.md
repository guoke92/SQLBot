# 召回架构改造实施计划（M1 确定性补召回基座 + M2 地图/缺口声明/门禁）

目标：杜绝 chatId=138 这一类失败——值实体（"研发二部"）桥不到 schema、planner 在局部视图上做出终局否定、澄清答案无法拓宽召回、SQL 引用工作集外的表无法自愈。全部为运行时改造，零 DB 迁移；已砍掉 schema_select/probe_agent；离线术语摘要（M3）本轮不做。

## M1 · 确定性补召回基座

### 1.1 值索引模块（新建 `backend/apps/datasource/recall/value_index.py`）
- 数据源：已发布字典值（复用 `apps/knowledge/dictionary_recall.py:54-88` 的过滤形状：oid+ds_id+enabled+READY+published_generation）∪ profiling 生效快照 `top_values`（`get_active_field_profiles`，`apps/datasource/profiling/service.py:422-439`；门控 `distinct_ratio ≤ 0.2`、每字段取前 20 值）。
- 条目：`{table_name, field_name, value, normalized_value, source}`；归一化复用 `normalize_dictionary_value`（`apps/dictionary/matching.py:10-12`）。
- 匹配 API：`match_values(text, *, oid, ds_id, session, access_scope)` — "归一化值 ⊂ 归一化文本"包含匹配（避开中文分词），值最短 2 字符，按 (table, field) 去重、值长度降序；结果过 AccessScope。
- 进程内缓存：模块级 dict + 锁 + 双检（照 `EmbeddingModelCache` 模式，`apps/ai_model/embedding.py:81-178`）；键 `(oid, ds_id)`，失效戳 = 字典 published_generation 聚合 + 各表 active_profile_generation 聚合，不匹配即懒重建。多进程各自持副本，可接受发布滞后。

### 1.2 补召回解析器 + 履行器（新建 `backend/apps/chat/steps/recall_topup.py`）
- `resolve_recall_topup(session, llm_service, *, signals) -> TopupManifest`：signals = {question_text, evidence_items（结构化 fields + 自定义文本）, unauthorized_tables, missing_concepts}。查找源按序：值索引 → 表目录词法（表名/custom_comment 匹配 missing_concepts 分词）→ 已选表的高置信关系邻接（`get_published_relations` 放宽到 confidence 门槛的 CANDIDATE，标 advisory）→ 知识单元索引（title/domain 匹配）。
- `fulfill_recall_topup(session, llm_service, manifest)`：`protocol.retrieve_schema(resource_names=并集, audit=False)` 精确投影扩表（不走 embedding 重排），更新 `chat_question.db_schema`/`table_name_list`，拼值证据文本块；无变化短路返回。
- 审计：`log_span(operate=CHOOSE_TABLE, graph_node="recall_topup")`（不新增 OperationEnum，遵守 span 约定）；遥测事件追加进 `QueryRun.agent_decision["topup"]`（现有 JSONB，不加列）。

### 1.3 澄清续跑增量重选（改 `retrieve_context_node` replan 分支，`nlq.py:1479-1496`）
- restore 快照后：读 `active_evidence(run_id)`；`clarification_option`/`user_correction` 的 `structured_value.fields[].table`（结构化，探查已确认存在）直接进强制带表信号；`clarification_custom`/`user_correction` 的 `content` 文本走值索引匹配。
- 解析+履行；工作集变化则 `capture_planning_context` 写回 `QueryRun.planning_context`（先例 `nlq.py:1511-1533`）——不写回会被下次 plan_query 的 restore 覆盖（关键约束：`nlq.py:2092-2095`）。
- 值证据经 `state["recall_topup_notice"]` 传入 planner 上下文。

### 1.4 T4 修复前扩表（改 `plan_query_node` failed_gates 分支，`nlq.py:2218-2272`）
- 构造 repair_hint 前：对带 `hard_gate_errors` 的 plan SQL 跑 `collect_sql_identifier_usage`（`apps/protocol/sql/identifier_validation.py:54-104`）→ physical_tables − table_name_list → 解析器地图查找 → 履行扩表 + 快照写回；修复重试在完整 schema 下自然进行。

### 1.5 功能开关（`common/core/config.py`）
- `RECALL_VALUE_INDEX_ENABLED: bool = True`、`RECALL_TOUP_ENABLED: bool = True`、`RECALL_TOUP_DS_ALLOWLIST: str = ""`（逗号 ds_id，空=全量）；布尔项必须登记进 `lowercase_bool` validator（`config.py:170-188`）。

### 1.6 M1 测试（根 `tests/`，遵循现有纯函数+SimpleNamespace/FakeStore 模式）

## M2 · 地图 + 缺口声明 + 门禁

### 2.1 `missing_concepts` 契约（`semantic_planning.py`）
- `QueryUnsupported` 加 `missing_concepts: list[str]`（无 before-validator，直接生效）；`NeedClarification` 加同名字段**且必须改 `coerce_payload`（semantic_planning.py:402-412，否则被重建 dict 剥掉）**。
- `_QUERY_AGENT_SYSTEM`（`query_agent.py:49-84`）更新 clarify/unsupported JSON 示例：声称缺失的概念必须列出。
- 策略：首轮 unsupported 且 missing_concepts 为空 = 协议不完整 → 门禁带提示打回一次；二次放行。

### 2.2 schema 地图 + 知识地图（新建 `backend/apps/chat/steps/recall_map.py`）
- `render_schema_map`：每表一行 `表名 | 注释 | ~行数`，AccessScope 过滤（复用 `project_schema_resources`）；分档：≤40 表全量、≤300 表按 database/schema 前缀分组、>300 域级摘要。
- `render_knowledge_map`：按 `_active_units`（`apps/knowledge/compile/compile.py:166-240`）的过滤条件查全部（不带 limit=2）已发布生效单元，`title | domain | description[:60]`，封顶 30 行 + "+N more"。
- 注入：`run_query_agent` 的 structured dict 加 `schema_map`/`knowledge_map` 两键（`query_agent.py:329` 一处调用）——不改 `PlanningContextSnapshot`（保持 v2，地图每次 plan 重算，廉价查询）。

### 2.3 `plan_gate` 节点（`nlq.py` 新节点 + `chat.yaml` 拓扑）
- YAML：`plan_query → plan_gate`（普通边）；`plan_gate` router `route_after_plan_gate` paths：`await_clarification / unsupported(→unsupported_query) / review_query / generate_queries / plan_query(反弹) / fail`。原 `route_after_planning` 逻辑作为共享函数被其调用，行为漂移最小化。
- NlqState 新增（JSON-only）：`topup_bounce_count: int`、`recall_topup_notice: dict`（已解析概念/新增表/值证据，反弹时注入 planner structured 上下文）。
- 门禁逻辑（确定性）：
  - unsupported：missing_concepts 逐个走解析器；命中且 `topup_bounce_count==0` → 履行扩表 + capture 写回快照 + 计数置 1 → 路由回 plan_query；未命中或预算已用 → 放行，misses 附进 unsupported payload（有据否定）。
  - clarify：选项 `ClarificationFieldRef.table` 引用的表不在工作集 → 同样反弹扩表（多数问题随之消失）。
  - ready：实体覆盖 advisory lint——值索引命中表 ∉ plan 实际表（`collect_sql_identifier_usage` 提取）→ 记 span + agent_decision.lint，不阻断。
- 反弹写回快照是生死线（见 1.3 同一约束）。

### 2.4 知识单元补召回（`compile_business_data_bundle` 加 `extra_revision_ids`）
- 突破"最多 2 个活跃单元"上限的方式：允许 +1（仅证据驱动补入），总预算仍受 planning_context 截断约束；测试并入 `test_semantic_knowledge_v2.py` 风格。

### 2.5 M2 测试
- `test_recall_map.py`（分档渲染/权限过滤/知识地图行数上限）、`test_plan_gate.py`（反弹一次有界/空 concepts 打回/无命中放行/ready lint advisory）、扩展 `test_query_unsupported_terminal.py`（路由经 plan_gate 后 unsupported 终局保证不变）、`missing_concepts` 解析测试（含 NeedClarification coerce 保留验证）。

## 验收与灰度
- 每层独立 flag + ds 允许名单；任一层关闭 = 精确回到现状行为。
- 最小评测脚本：回放历史 chat_record（成功用例已知用表 + 全部 SCHEMA_NOT_SUPPORTED 失败用例）对解析器打分：表召回@k、值命中率、门禁准确率（无 LLM 参与，可进 CI）。
- 验证命令：`cd backend && ./venv/bin/python -m pytest ../tests/<file> -v`；`bash scripts/lint.sh` / `bash scripts/format.sh`。
- 收尾更新 `AGENTS.md` 热路径表（plan_gate 节点）与 `docs/` 设计文档。

## 明确不做 / 边界
- 不做：probe_agent/schema_select（已砍）、离线术语摘要（M3 后续）、错误包装链路修复（第三方负责）、静态阈值改动。
- 排除面：REST 协议数据源（值索引/地图仅 SQL 数据源）、out-DS assistant 路径。
- 残留风险（记录在案）：ready 路径口径正确性无法确定性验证，仅靠知识地图可见性缓解；值索引是存在性探测器，已限定 AccessScope 内且只返回表/字段位置。
