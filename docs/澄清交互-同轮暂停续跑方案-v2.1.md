# 澄清交互统一方案 v2.1：同轮暂停 / 续跑（唯一路径）

> **版本**：v2.1（相对 [澄清交互-同轮暂停续跑方案-v2.md](./澄清交互-同轮暂停续跑方案-v2.md)；**不修改** v1/v2 原文）  
> **配套**：[查询契约与NLQ整体优化方案-v2.1.md](./查询契约与NLQ整体优化方案-v2.1.md)  
> **现行实施以本文件 + 整体 v2.1 为准**

原则不变：**一条 record、一种暂停、一个续跑入口、一套状态**；删除父子 record；不做存量兼容。

---

## 0. 相对 v2 的决议补强

| 缺口 | v2.1 钉死 |
|---|---|
| 推荐缺失导致逃生口失效 | **下发卡的每道题必须有有效 recommended**；否则补推荐或删题，禁止无推荐题进卡 |
| 多端 / 无 UI | **唯一策略**：无澄清 UI 时，全题有推荐 → 服务端等价 `accept_recommendations`；否则 **failed「需要交互确认」**，不生成 |
| 自定义扩题 | **规范化器硬约束**：continue 后再评估不得新增第 1 轮白名单题（仅冲突类且 round&lt;2） |
| 未完成 record | 列表/限流：`awaiting_input` 算进行中；过期（默认 24h）→ failed「确认超时」 |

其余 v2 内容（pause/continue/cancel、工程契约、删父子）全部继承。

## 2. 唯一生命周期

```text
created → running → awaiting_input ⇄ running → terminal
                         ↑ 最多再进 1 次（第 2 卡）
terminal ∈ { success | degraded | failed }
```

| 字段 | 含义 |
|---|---|
| `outcome.status` | `running` / `awaiting_input` / `success` / `degraded` / `failed` |
| `intent_context` | draft / questions / answers / contract / assumptions |
| `finish` | 仅 terminal 为 true；`awaiting_input` ⇒ false |
| `clarification_round` | `1` \| `2` |

### SSE

```text
awaiting_input → clarification + awaiting_input（可关连接，未 finish）
terminal       → finish + outcome（含 explain，见整体 v2.1）
```

## 3. 唯一 API

### 3.1 首问

`POST /chat/question` — 无 `clarification_*`。  
同 chat 已有 `awaiting_input` → **拒绝**新问（明确错误码），前端引导确认或 cancel。

### 3.2 续跑

```http
POST /chat/record/{record_id}/continue
Body: {
  "mode": "answers" | "accept_recommendations",
  "answers": ClarificationAnswer[]   // mode=answers 时必填
}
```

| mode | 行为 |
|---|---|
| `answers` | 显式选项/自定义 → merge |
| `accept_recommendations` | 本卡**每题**均有合法 recommended → 合成 answers + assumptions |

缺推荐 → 4xx，不得部分静默。

### 3.3 取消

`POST /chat/record/{record_id}/cancel` → failed，finish=true。

### 3.4 工程契约

- 幂等 / 禁双开图  
- `custom_text` 原文保留  
- **禁止**等待超时自动生成；仅用户 continue/cancel 或 **24h 过期任务** → failed  
- 多标签：一端 cancel 后另一端 continue → 明确 409/状态错误  

### 3.5 无澄清 UI 通道（MCP / markdown / 无卡客户端）— 唯一策略

在将要 `pause_intent` 时：

```text
if 通道不支持交互澄清:
  if 每题均有合法推荐:
    内部等价 accept_recommendations → 不 pause，直接续跑生成
    assumptions 标记 accepted_recommendation + channel=non_interactive
  else:
    failed（需要交互确认）→ finish=true，不生成 SQL
```

禁止：非交互通道静默清空问题硬跑；禁止再开第二套「MCP 专用澄清协议」。

## 4. 图入口

同一 `chat`，`run_mode = start | continue`。

```text
start    → … → assess_clarity →（出题闸含推荐强制）→ pause | assemble | fail
continue → hydrate_resume → assess（若需）→ pause | assemble | fail
```

- `pause_intent` 不 finish  
- 执行后路径 **禁止** pause  
- hydrate 失效 → 已有 retrieve/ground，不复制逻辑  
- P1 真 checkpoint **替换** hydrate，不并行  

---

## 5. 出题闸（交互侧，与整体方案共用一处实现）

下发前必须全部满足：

1. 选项 `set` requirement 过 schema/`field_reference`  
2. 非法选项剔除；题无合法选项 → 删题  
3. **每题必须有指向仍存在选项的 `recommended_option_ids`**；否则：模型补全失败则删题或评估重试，**禁止无推荐进卡**  
4. 题量：目标 1～2，硬顶 4；第 2 轮硬顶 2  
5. 过滤后零题 + 可执行 → ready；零题 + 不可执行 → failed（或评估重试 1 次）  

### 自定义后再评估（硬约束）

- 已结构化确认的槽位锁定  
- **不得**新增 `clarification_round==1` 白名单类新题  
- 仅当 `clarification_round < 2` 且属于「确认不可执行 / 互斥」时可出第 2 卡  
- 违反则规范化器丢弃扩题，改 assumption 或 failed  

---

## 6. 前端

同 record 一条助手气泡；支持作答 / 按推荐继续 / 取消。  
仅当每题有推荐时展示「按推荐继续」。  
列表将 `awaiting_input` 标为待确认；支持从历史恢复作答。

---

## 7. resume 状态

同 v2：`intent_context` + `clarification_round` + `resume_cache` + run_lock。  
过期任务扫描写入 failed。

---

## 8. 验收（相对 v2 增量）

- 下发 questions **无**缺推荐题  
- 非交互通道：全推荐则自动采用并记假设；否则 failed，不生成  
- 自定义后再评估不出现新的第 1 类业务题  
- 暂停 &gt;24h 不可 continue  
- 其余继承 v2 验收  

---

## 9. 一句话决议（v2.1）

> **同 record 暂停澄清；continue 仅作答或采用推荐；进卡必须有推荐且过 schema；无 UI 通道自动采用推荐或明确失败；删除父子澄清与静默跳过。**
