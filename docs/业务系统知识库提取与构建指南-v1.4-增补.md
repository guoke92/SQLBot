# 业务系统知识库提取与构建指南 v1.4 增补

> 配套：《业务系统知识库提取与构建指南-v1.md》（v1.3）、《知识体系目标架构-v3.1.md》（ADR）。
> 本增补定义提取侧为支撑节点化存储与图召回所新增的三项产出纪律。v1.3 的全部方法论（两遍提取、权威顺序、EvidencePack、覆盖矩阵）不变。

## 1. concept 必须锚定字段（field_targets）

概念不再只是"一段业务解释"。每个 concept 必须声明 `field_targets`，指向**本单元已声明的字段**：

```yaml
concepts:
- concept_id: authorization-agreement
  name: 授权协议
  aliases: [已认证协议]
  definition: 企业在某产品上的授权协议签署记录。
  dictionary: {Y: 已认证, N: 未认证}
  field_targets:                      # 新增：概念锚定的字段
  - dataset: agreement
    field: authed_status
```

规则：
- 状态类概念锚定到承载其字典的字段；字典跨两个字段时（如 建档中 = build_status 的 CUST_BUILDING + check_status 的 CUST_CHECK_*）**两个都写**。
- 实体类概念（概念即一张表，如"股东出资"→cust_shareholder_info）锚定到该表的 `id` 字段（或业务键字段）。
- 无锚定概念的包可通过 lint（CONCEPT_UNANCHORED）与存量桥脚本 `scripts/infer_concept_anchors.py` 识别/补齐，但**新提取必须直接产出**。
- 概念的字典键值与锚定字段的字典键值应一致（键一致是硬要求，值措辞可有详略差异）。

## 2. 包级 relationships 作为一等产出

跨单元的物理表关系写入包级 `relationships`（manifest 顶层或独立 `relationships.yaml`，导入时并入契约）：

```yaml
relationships:
- left_table: authorization_agreement
  left_field: cust_id
  right_table: cust_company_info
  right_field: id
  evidence: write-flow:CustAuthAgreementDomainServiceTest.java
```

规则：
- **端点用物理表名/字段名**（不是单元内 dataset_id）——关系天然跨单元。
- 端点字段允许不被任何单元声明（字段级最小声明的自然结果）：运行时会生成 stub 节点并在绑定时对活库校验（lint RELATION_UNDECLARED_ENDPOINT 会提示）。
- 每条关系必须带 evidence（write-flow / read-flow / java-eq / ref-convention）。
- 单元内部关系仍写在单元 `content.relationships`（dataset_id 引用），两处互补。

## 3. unit_links：跨场景语义方向

需要声明**推导不出来**的跨单元语义（数据耦合 shares_data 由运行时推导，**禁止声明**）：

```yaml
unit_links:                          # 单元顶层字段（与 aliases 同级）
- target_unit: enterprise-onboarding # 建档是本单元（签约）的前置流程
  kind: prerequisite                 # prerequisite | validates
  via:                               # 证据字段（本单元已声明）
  - dataset: company
    field: build_status
  evidence_refs: [ev-sign-service-checks-build-status]
  description: 签署前校验企业建档状态为审核通过。
```

规则：
- `kind` 仅两种：`prerequisite`（目标单元是本单元的前置业务流程）、`validates`（本单元执行时校验目标单元的状态）。
- `target_unit` 必须是同包内已存在的 unit_id；`via` 必须解析到**本单元**的 dataset/field（闭包硬校验）。
- `evidence_refs` 必填且指向包内证据（闭包硬校验）；空证据会被 lint（UNIT_LINK_UNJUSTIFIED）标记。
- 只有代码能证明调用链/状态校验时才声明；拿不准就不写——缺一条 unit_link 只损失召回广度，错一条会污染扩展。

## 4. 字段级最小声明与"声明即边"

共享表（如 cust_company_info）在**每个用到它的单元里照常声明**（保持单元自包含），但只声明被本单元**读/写/锚定/约束**的字段：

- 被 data_effects 引用（reads/writes）✓
- 被 concept.field_targets 锚定 ✓
- 被 caliber/rule.field_targets、metric.field/grain 约束 ✓
- 被 relationships 端点引用 ✓

未被以上任何一项引用的声明字段会被 lint（FIELD_DECLARATION_ORPHAN）标记——要么补上引用它的知识，要么删掉声明。

## 5. 每层铺业务词（召回质量的前提）

运行时按节点做向量+词法混合检索，索引文本来自各层内容，因此：

- 字段 description 用业务话术写清楚（"签署记录""企业业务键"），不要留空。
- 字典值必须带含义（`Y: 已认证`），状态字段尤其如此。
- stage 的 name/trigger 用业务动词（"查询已签署协议企业"），不要用方法名直译。
- concept aliases 尽量覆盖用户口语（签约/已认证协议/授权协议）。
