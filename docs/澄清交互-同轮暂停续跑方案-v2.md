# 澄清交互统一方案 v2：同轮暂停 / 续跑（唯一路径）

> **版本**：v2（相对 [澄清交互-同轮暂停续跑方案.md](./澄清交互-同轮暂停续跑方案.md) 的改进版；**不修改** v1 原文）  
> **配套**：[查询契约与NLQ整体优化方案-v2.md](./查询契约与NLQ整体优化方案-v2.md)  
> **依据**：Cursor / OpenCode / Kimi 人机协同，以及 ChatBI / AmbiSQL 等消歧实践对照分析  

原则不变：**一条 record、一种暂停、一个续跑入口、一套状态**；删除父子 record 双轨；不做存量兼容。

---

## 0. 相对 v1 的主要改进

| 改进 | 来源启发 | 内容 |
|---|---|---|
| 显式逃生口 | Kimi「做个全面的研究」 | **按推荐全部继续**（非静默跳过） |
| 出题质检闸 | AmbiSQL / ChatBI schema 消歧 | 选项绑定必须过 schema，不过不下发 |
| continue 工程契约 | Cursor AskQuestion 回灌/超时事故 | 幂等、原文保留、禁止超时静默 skip |
| 题量目标 | ChatBI 短澄清 | 目标 1～2 题，硬顶 4；第 2 卡 ≤2 |
| 暂停中新问 | OpenCode session 单一 | 写死一种策略：须先确认或取消 |
| 与权限分轨 | OpenCode question ≠ permission | 本产品仅意图暂停；不与工具审批混模型 |
| 可观测 | 业界运维常识 | 澄清率 / 推荐续跑率 / continue 失败码 |

## 1. 删除面（与 v1 相同，仍整段删除）

- `clarification_parent_id` / `clarification_for_record_id`  
- `prepare_question_intent` 的 parent 分支  
- 澄清走 `questionApi.add` + 新用户气泡  
- `complete_intent` 把等待当成 `terminal finish`  
- 前端靠 child record 判断已答  
- 任何「过渡期双写 parent + continue」  

旧 awaiting 卡直接失效。

## 2. 唯一生命周期

```text
created → running → awaiting_input ⇄ running → terminal
                         ↑ 最多再进 1 次（第 2 卡）
terminal ∈ { success | degraded | failed }
```

### 状态唯一真相

| 字段 | 含义 |
|---|---|
| `outcome.status` | `running` / `awaiting_input` / `success` / `degraded` / `failed` |
| `intent_context` | draft / questions / answers / contract / assumptions |
| `finish` | **仅 terminal 为 true**；`awaiting_input` ⇒ `finish=false` |
| `clarification_round` | `1` \| `2`（可放 intent_context 内） |

禁止第三套「是否在等澄清」标志。

### SSE（传输结束 ≠ 业务结束）

```text
awaiting_input → event: clarification + awaiting_input → 连接可关；record 未 finish
terminal       → event: finish；record.finish=true
```

前端禁止用「流结束」推断完成。刷新后若仍 `awaiting_input`，卡可继续作答。

## 3. 唯一 API 面

### 3.1 首问

```http
POST /chat/question
Body: { chat_id, question, ... }   # 无 clarification_* 
→ SSE on record R
```

### 3.2 续跑（唯一答案入口）

```http
POST /chat/record/{record_id}/continue
Body: {
  "mode": "answers" | "accept_recommendations",
  "answers": ClarificationAnswer[]   // mode=answers 时必填
}
→ SSE on 同一 record_id
```

**`mode` 语义（v2 新增）：**

| mode | 行为 |
|---|---|
| `answers` | 用户显式选项/自定义；走 `merge_clarification_answers` |
| `accept_recommendations` | **仅当本卡每道题都有 recommended_option**；按推荐合成 answers，并写入 assumptions（`code=accepted_recommendation`） |

无推荐或任一带缺推荐 → **拒绝** `accept_recommendations`（4xx），不得部分静默。  
这不是「跳过澄清」，而是 **显式确认采用系统推荐**（对齐 Kimi 跳过，但保留可审计假设）。

实现三步（单函数，禁止第二入口）：

1. 校验 `awaiting_input` + 归属 + 未在续跑中  
2. 按 mode 得到 answers → merge → 更新 intent_context  
3. `submit_graph("chat", { run_mode: "continue", record_id })`  

### 3.3 取消

```http
POST /chat/record/{record_id}/cancel
→ failed（用户取消），finish=true
```

### 3.4 continue 工程契约（v2 必做）

| 规则 | 说明 |
|---|---|
| **幂等** | 同一 record 在已进入 `running` 后续跑后，重复 continue 返回明确错误或返回进行中状态，**禁止**双开图 |
| **原文保留** | `custom_text` 原样入库与回灌，禁止改写/近义替换（对齐 Cursor 自由文本失真教训） |
| **禁止超时静默 skip** | 服务端不得因等待过久自动 `accept_recommendations` 或清空问题继续生成；仅用户 continue/cancel 或业务过期任务 |
| **过期** | 可选：暂停超过 T（如 24h）→ 后台标 failed「确认超时」；卡不可再 continue |
| **并发新问** | **唯一策略**：同 chat 存在 `awaiting_input` record 时，新 question **拒绝**或提示先确认/取消（实现只选拒绝+明确错误码，前端引导 cancel） |

## 4. 唯一图入口

同一 `chat` graph，`run_mode = start | continue`。

```text
start    → … → assess_clarity → ready? assemble : pause_intent | fail
continue → hydrate_resume →（必要时同 assess）→ ready? assemble : pause_intent | fail
```

- `pause_intent`：只负责 `awaiting_input` 持久化 + SSE；**不** `finish=true`  
- 不懂 / 澄清系统异常：走 `fail`，与 pause **分节点**  
- `hydrate_resume`：只灌状态；缓存失效则路由到**已有** retrieve/ground 节点，不复制业务逻辑  

`decide_next` / 执行后路径：**禁止**再进入 `pause_intent`（有数后的契约偏差只评分）。

---

## 5. 出题与暂停内容（交互侧闸门）

出题规则的业务白/黑名单见整体方案 v2；交互层强制：

1. **下发卡前**：每个选项的 `set` requirement 做 schema/`field_reference` 校验；整题无合法选项 → 删题或改 assumption，**不得**把坏题发给用户。  
2. **题量**：目标 1～2，硬顶 4；第 2 轮硬顶 2。超限合并或降级为 assumption。  
3. **推荐续跑按钮**：仅当 `accept_recommendations` 前置条件满足时由前端展示。  
4. **自定义**：允许；merge 后若需再评估，不得借机把第 1 轮白名单题再扩一轮（口子收窄规则见整体 v2）。

## 6. 前端唯一路径

```text
一条 user + 一条 assistant(R)
  → SSE：clarification / awaiting_input
  → 用户：选项提交 | 按推荐继续 | 取消
  → POST continue / cancel
  → 同一 assistant 续接 SSE → finish
```

删除澄清专用 `sendMessage`、parent/child 查找。  
卡 UI 须同时支持：逐题作答、`accept_recommendations`、cancel。

## 7. resume 状态（一份）

落在同一 ChatRecord：

```text
intent_context
clarification_round
resume_cache: schema_fingerprint, bindings, temporal, ds_id, …
continue_token / run_lock（防双开，实现可选）
```

禁止再查父子 record 拼上下文。

## 8. 模块职责（防双轨）

| 模块 | 职责 |
|---|---|
| `api/chat.py` | question / continue / cancel 三端点 |
| 单 continue service | merge + 锁 + 启图 |
| `pause_intent` | 仅暂停 |
| `hydrate_resume` | 仅灌状态 |
| `ClarificationCard` | answers / accept_recommendations / cancel |

---

## 9. 验收（v2 增量）

在 v1 验收基础上增加：

- 每题均有推荐时，`accept_recommendations` 可一次续跑，并产生 assumptions  
- 缺推荐时该 mode 被拒绝  
- 坏绑定选项不得出现在下发 questions  
- 重复 continue 不双开图  
- custom_text 往返一致  
- 无「等待超时自动生成 SQL」  
- 同 chat 暂停中新 question 行为符合唯一策略  

---

## 10. 一句话决议（v2）

> **同 record 上 `awaiting_input` 暂停；答案只经 `continue`（显式作答或显式采用推荐）；取消经 `cancel`；删除父子澄清；出题先过 schema 闸；续跑工程契约防双开与静默跳过。**
