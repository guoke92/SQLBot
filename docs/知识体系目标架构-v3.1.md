# 知识体系目标架构 v3.1（ADR）

> **已废止作为运行权威（2026-09-15）。** 问数 Wiki 以 [`docs/wiki/`](wiki/README.md) 为准。本文仅为旧 unit/semantic ADR 历史。

## 1. 背景与问题

现行 2.0 实现以 `knowledge_unit_revision.content`（场景单元 JSON）为唯一可编辑真相、发布仅投影 K3 术语、召回以整单元为细胞（≤2 个）。端到端验证暴露出四个结构性问题：

1. **复制税**：v4 提取包中 `cust_company_info`（含 build_status 的 14 值字典）被复制进 14/22 个单元；修正一处字典需改 14 个 revision。
2. **检索盲区**：K3 只投影单元级词汇（title/aliases/concept 名），字段/流程/字典词汇不入索引——"已签约的企业有多少"在现行召回下无法命中（"签约"不在任何单元投影词表中）。
3. **跨域断链**：六层图的 L2→L1（concept→field）边无生产原料——`ConceptDefinition` 没有 `field_targets`，而 caliber/rule/metric 都有。
4. **包级关系孤儿**：v4 的 `relationships.yaml`（72 条带代码证据的物理关系）在契约 schema 之外，运行时无法导入。

## 2. 架构决策

| # | 决策 | 理由 | 被否决的替代 |
|---|---|---|---|
| D1 | 节点化真相（六层节点）+ 单元组合治理 + 发布钉扎 | 消灭复制税；单元仍是审核对象，防 1.0 扁平条目复燃 | 保留单元 JSON 为真相（改 14 处） |
| D2 | 运行时只读不可变快照（composition_deployment 物化） | 发布不可变、回放可复现、节点编辑不静默影响线上 | 运行时直查节点库（版本漂移） |
| D3 | 图在 Postgres（邻接表 + 递归 CTE） | 万级节点/1–2 跳闭包毫秒级；保住单库事务原子性 | 图数据库（Neo4j 等——见 §7 触发条件） |
| D4 | 运输契约渐进演进：附加可选字段、schema_version 保持 2.0、旧包有效 | 提取侧平滑过渡；v4 等存量包不需重提取即可导入 | 契约版本升级（破坏存量） |
| D5 | 全层节点索引（不只术语） | 消灭字段/流程/字典词汇的检索盲区 | 仅扩 K3 投影词表（治标） |
| D6 | 去重归并在分解器；提取侧保持单元闭包 + 字段级最小声明 | 单元自包含是引用闭包的基础；归并是导入关注点 | 提取侧表级去重（破坏闭包、重做引用体系） |
| D7 | 权威顺序 = 三合并点规则：M1 提取多源（库值＞代码＞文档＞skill）/ M2 导入归并（PUBLISHED 胜出→冲突队列）/ M3 bind 活库（Catalog 无条件胜出） | "库值第一"在 M3 无条件保证，M1 有画像时提前生效 | 库值只放 bind（丢失提取期画像价值） |
| D8 | 声明即边：单元内声明的每个字段必须被 concept_of/reads/writes/references_field 引用 | 最小声明可自检；声明本身成为边的证据 | 自由声明（回到全量复制） |

## 3. 六层节点模型与边来源映射

节点层：L0 证据（不可变追加）→ L1 物理锚点（dataset/field/relation）→ L2 概念 → L3 流程（stage）→ L4 口径约束（caliber/metric/rule）→ L5 范例（query_pattern）。上层通过类型化边引用下层。

| 边类型 | 连接 | 契约原料 | 状态 |
|---|---|---|---|
| has_field | dataset→field | datasets.fields（结构边，恒 confirmed） | 已有 |
| concept_of | L2→L1 | **concept.field_targets（P0 新增）** | P0 落地 |
| references_field | L4→L1 | caliber/rule.field_targets、metric.field+grain | 已有 |
| reads / writes | L3→L1 | data_effects.operation/dataset/fields | 已有 |
| relation_endpoint | L1↔L1 | 单元 relationships + **package.relationships（P0 新增）** | P0 落地 |
| precedes（单元内） | L3→L3 | stage.next_stages | 已有 |
| precedes（跨单元） | L3→L3 | **unit_links kind=prerequisite/validates（P0 新增）** | P0 落地 |
| shares_data | 组合↔组合 | **不声明**，分解器从共享 dataset 节点推导 | P1 落地 |

## 4. 契约演进（P0 已实现）

- `ConceptDefinition.field_targets: list[SemanticFieldRef]`（可选，lint CONCEPT_UNANCHORED advisory，后续升 blocking）
- `KnowledgePackageV2.relationships: list[PackageRelationship]`（物理表名端点；**不做单元闭包硬校验**——v4 实测 72 条关系中 4 个表级/19 个字段级端点未在单元声明中出现，属字段级最小声明的自然结果；lint RELATION_UNDECLARED_ENDPOINT 提示，分解器生成 stub 节点，bind 活库校验）
- `KnowledgeUnitEntry.unit_links: list[UnitLink]`（target_unit 必须存在于包内；via 必须解析到声明单元的 dataset/field；evidence_refs 收入证据闭包；shares_data 禁止声明）
- 存量桥接：`scripts/infer_concept_anchors.py`（v4 实测 44/44 全锚定：字典键分区/字典值提及/dataset token 匹配三规则）

新增 lint 规则：CONCEPT_UNANCHORED、UNIT_LINK_UNJUSTIFIED、FIELD_DECLARATION_ORPHAN、RELATION_UNDECLARED_ENDPOINT（均 advisory）。

## 5. 存储与治理（P1–P2）

- 新表（迁移 096）：knowledge_node / knowledge_node_version / knowledge_edge / unit_composition / composition_binding / composition_deployment / knowledge_node_index / knowledge_merge_conflict
- 分解器：register_package 末尾挂接（双写过渡）；物理键归并（dataset=norm(db.table)，空 database 按 name 归并、同名异库进冲突队列）；PUBLISHED 载荷冲突必进队列不静默
- 发布：钉扎节点版本集合 → assemble_composition() 物化快照（**单代码路径同时服务审核视图与发布**）→ 原子构建节点索引（embedding 失败整体回滚）→ ACTIVE 切换；节点更新后组合标 NEEDS_REVALIDATE
- 漂移：schema_drift 信号改打 dataset/field 节点 → 组合待复验（修复现行 L-1 打空表问题）

## 6. 召回（P3）

两段式：混合种子检索（向量 + pg_trgm 词法 + 物理键精确，top 8–12）→ 有界闭包 → delta 切片 → 三层预算（floor/流程/跨域）。

**双类跳数语义**：语义跳（concept_of/reads/writes/relation_endpoint/precedes，双向，confirmed-only）≤2 跳；结构跳（has_field 轮毂展开）不计跳数、受配额约束（字段≤12/关系≤6/阶段≤4/口径≤3/范例≤2）。种子命中后其归属 dataset 字段切片直接进 floor。

质量护栏：确定性排序 (精确命中数, 检索分, node_key)；proposed 边命中转澄清候选；跨域扩展必须有数据边证据；评测集（≥60 题含 ≥15 跨域）双跑 ≥2 周，阈值：种子命中≥unit 基线、闭包精确率≥60%、token 降≥30%、跨域题命中≥80%。开关 `KNOWLEDGE_RECALL_STRATEGY` 默认 unit，评测通过后切 node。

效率：v4 规模 ~1.5K 节点/3–5K 边，端到端新增延迟 <20ms；token 较整单元 floor 预估降 5–10 倍。

## 7. 图引擎触发条件（不做的退出条款）

以下全部满足时重评图数据库：①节点/边达百万级且持续增长；②常态查询深度 ≥3 跳且需路径语义；③发布原子性可接受跨库最终一致；④全图算法（PPR/社区发现）成为在线召回主路径。

## 9. 与现行实现的关系

**保留复用**：scanner 与 KnowledgePackageV2 契约、四态生命周期、发布原子性模式（with_for_update/BUILDING→ACTIVE/ERROR 回滚）、_projection_embeddings 原子语义、budget_context_sections 预算机制、BusinessDataBundle 槽位契约、planning_context 快照回放、evidence 台账 + lineage 事件 + apply_log 审计、scope_knowledge_matches 权限过滤、审核中心三 Tab UX、capture job 队列。

**改对象复用**：bind_and_validate（对象从 revision JSON 换成节点组合）、knowledge_asset/knowledge_schema_ref 死表（改造为节点库骨架参考）、L-1 漂移信号（从打空表改为打节点）。

**退役**：K3-only 投影、整单元 floor 展开、_STATE_TOKENS 硬编码、VQR 死路径（P3 由节点 embedding 自然修复）、knowledge_package_registry、terminology 与 K3 投影共表无隔离。

**复活**：staging 候选（→ inbox 晋升/否决，见 feedback.py）、L-3 join 候选（→ relation_endpoint proposed 边）、VQR 复用（P3 由节点 embedding 提供真实相似度）。promote_to_trusted 等 1.0 治理函数仍未接线（节点信任分级待后置设计）。

> **data_training 结论修订**：P4 落地时确认 few-shot 范例不锚定数据表、无法成为 KnowledgeUnitEntry（契约要求 ≥1 dataset），故**不**迁为 query_pattern 节点；建议后续并入“绑定时的 VQR 校验”或为无数据集范例单独设计 schema 关联。

## 10. 落地状态与遗留
