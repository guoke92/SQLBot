# 第一部分：摸清现状

## 1. 现在系统里实际有什么

2.0 **已经落地**，不是待开工的方案。代码主路径是：

```text
导入 2.0 包
  → knowledge_package / evidence / unit / revision（Draft）
  → 推荐数据源、绑定、校验
  → 审核中心按单元处理
  → publish 写入 K1–K5 投影
  → compile_business_data_bundle 从 PUBLISHED revision JSON 展开
  → Query Agent
```

页面已是三 Tab：审核中心、运行时知识、知识包。文件/文件夹/ZIP 导入已统一相对路径。

**同时还活着的旧平面（1.0 / 积累架构）：**

```text
术语 CRUD、数据训练、关系管理、配置助手
对话 capture → submit_candidate → KnowledgeStaging → certify_*
knowledge_package_registry（088，条目 readiness）
BusinessDataBundle 底部的 bound_calibers / matches / examples 影子
```

所以现状不是「纯 2.0」，而是 **2.0 骨架 + 旧写入面未拆除 + 编译层两边都接**。

## 2. 2.0 方案本身是否合理

**合理，而且方向对。** 1.0 把「建档」拆成术语、规则、关系、示例之后，审核看不到场景，问数也无法一次拿回定义+状态+表+口径。以知识单元为审核/版本/发布主体，这个判断成立。

**因此：不推倒 2.0，不回到扁平条目。**

## 3. 2.0 里值得留下的设计

- 单元必须能回答「概念 → 对象 → 状态 → 字段 → 关系 → 口径 → 查法」
- 证据不可改，修改出新 revision
- 物理真实性不交给 LLM
- 未发布不进运行时；缺表是包级诊断
- 发布失败旧版继续服务
- 不引入图库、不建 SQL 编译器

## 4. 现状局限

闭环写反：STALE 后知识蒸发；绑定要求 CONFIRMED、CONFIRMED 却在发布才写；导入要求查询已 executed；助手不展开单元；FAIL 写成 UNBOUND；包状态与四态竞争。

双轨：术语/训练/capture 仍直写运行时；compile 双接；Query Agent 仍留术语/训练字符串槽。

过重：归并引擎、证据新表、单元向量层、Ossie、一张表一个单元、先删配置助手 API。

内容缺口：v3 仍是 1.0 items，须按 2.0 单元重编，不做自动升格。

## 5. 现状结论

```text
2.0 方向正确，骨架可用。
问题 = 闭环写反 + 旧平面未拆 + 编译双接 + 对话未按槽位用知识。
对策 = 把 2.0 做完整、做瘦，而不是再叠一层框架。
```

# 第二部分：目标架构

## 6. 五层

```text
L0  离线提取  文档先建业务索引 → 代码/DB 闭环 → 2.0 场景单元包
L1  登记      包 + 不可变证据 + Draft revision（唯一写入面）
L2  绑定校验  Catalog 对照；查询后置执行；关系允许 proposed
L3  审核发布  单元为主体；ACTIVE 指针原子切换；只写 K3 定位索引
L4  问数编译  定位 1～2 个 ACTIVE JSON → 按问题裁剪 → Bundle
Query Agent 只读 Bundle 语义槽位 + schema + 字典 entity_bindings
```

反馈、对话沉淀、人工修改：追加证据或新 Draft，回到 L1。L4 不写知识。

没有：图数据库、通用 SQL 编译器、独立流程资产、Staging 认证平面、第二套 Planner 知识协议、产品内提取器。

## 7. L0 完整形态（提取合同）

提取器留在离线。SQLBot 只接收已经闭环的 2.0 包。

### 7.1 两种产物，不要混

- **证据包 / 业务索引**（工作目录，不入库、不进 Prompt）：源材料目录、域/模块地图、术语候选、流程草稿、冲突清单、**场景目录**（domain → unit_id → 问数适用性）。
- **2.0 知识单元包**（唯一导入物）：每个单元是一个可问数的业务场景闭环。

对话沉淀默认是证据碎片，不够成单元。

### 7.2 一个完整单元必须能回答

用户说一个业务词时，一次给出：概念与别名、对象粒度、流程状态与 data_effects、表字段字典、proposed 关系、会改变 SQL 的口径/规则、proposed 查询范式、证据（文档+代码+表）。缺「绑到真实字段」不算提取完成。代码规范、模块划分、skill 调用方式、治理说明书不是单元内容。

槽位：`title/aliases/domain/applicability` + `concepts` + `processes.data_effects` + `datasets.fields` + `relationships` + `calibers/metrics` + `domain_rules` + `query_patterns` + `evidence_refs`。

### 7.3 两遍提取

第一遍：skills / 业务规则 / 代码地图 / 需求设计 → 场景索引（不写单元）。skill 只导航，规范禁止写成 domain_rules，文档与代码冲突标 conflicts，文档不赢。

第二遍：Controller → Service → MyBatis → DB 把索引闭环。权威顺序：库字段和值 > 代码读写 > 文档主张 > skill 导航。

第三遍：同一 scenario_id 收成一个单元。不要拆回 1.0 条目。

### 7.4 包内体系（三层，不加图谱）

```text
业务系统包（namespace）
  └── 业务域（unit.domain）
        └── 场景单元（unit_id）
```

包是目录与证据合订本，无生命周期、不召回。域是审核分组，不单独立表。单元是唯一可发布、可召回、可进 Prompt 的细胞。跨场景最多同时召回 2 个单元，靠共享表名拼接，不建单元关系图。

## 8. 存储：一份真相，一种索引

可编辑真相只有 `knowledge_unit_revision.content`。

发布后只写 **K3 术语**（带 `unit_revision_id`）作定位索引。K1/K2/K4/K5 停写新行——compile 已从单元 JSON 展开关系/口径/规则/已验证查询。Staging / 1.0 registry 停写。

关系：`proposed | confirmed`，导入默认 proposed。查询：导入不要求已执行；verification 写入 `binding.mapping`。

## 9. 正交四态与对话可见性

- 生命周期：`DRAFT → IN_REVIEW → APPROVED → PUBLISHED`
- 绑定：`UNBOUND` / `BOUND`（FAIL 仍 BOUND）/ `STALE`（本单元表字段 fingerprint 变了）
- 校验：`NOT_RUN | PASS | WARNING | FAIL`
- 部署：`BUILDING | ACTIVE | ERROR | RETIRED`

包无生命周期，只留最近一次包级诊断。

| 状态 | 问数召回 |
|---|---|
| DRAFT / IN_REVIEW / REJECTED / APPROVED 未发布 | 否 |
| PUBLISHED + ACTIVE + BOUND | 是 |
| PUBLISHED + ACTIVE + STALE | 是（内容仍是已发布 JSON） |
| ERROR / RETIRED | 否 |
| 助手 | 与主对话同一规则，保留 ds_id |

澄清轮次复用检索快照，不重新抽签。发布失败不切指针。

## 10. 绑定与校验

登记 → 推荐源 → 绑定（datasource + 本单元表字段 fingerprint）→ 校验字段存在/类型、查询只读执行、关系两端存在。proposed 关系 → WARNING。缺表缺字段 → FAIL，binding 仍 BOUND。

## 11. 召回稳定与 Query Agent 槽位

同一 `question + datasource_id + 当前 ACTIVE 集合` → 同一组 `unit_id`（最多 2）。

定位：精确标题/别名/概念 ⊂ 问题 → K3 `unit_revision_id` → 排序 `(精确命中数, K3 分, unit_key)`。无命中则 Bundle 无单元，只靠 schema，禁止灌全部已发布单元。

裁剪：必带命中相关 datasets/fields/关系；口径/规则按词相交；状态词才带 process；verified 查询最多 2 条。预算截断先丢 process/证据，后丢口径和字段。

Query Agent 只读：`matched_units`、`concepts`、`processes`/`data_effects`、`datasets`/`fields`、`relationships`（JOIN，不问用户）、`calibers`/`metrics`（默认必须用）、`rules`、`verified_examples`、`conflicts`/`assumptions`（只澄清）。`apply_log` 走审计，字典走 `entity_bindings`。

## 12. 交互

三 Tab。知识包：导入与包级绑定/诊断。审核中心：按 domain 分组，主按钮 = next_step。运行时：只列 ACTIVE，STALE 标记，同一套单元抽屉。

## 13. 明确不做

1.0 兼容导入、自动升格、图数据库、Ossie、通用 SQL 编译器、单元向量新索引、语义归并服务、产品内提取器、Query Agent 内再做知识规划、为修闭环加新表。
