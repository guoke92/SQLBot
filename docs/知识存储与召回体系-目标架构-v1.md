# 知识存储与召回体系 · 目标架构 v1

> 日期：2026-08-11
> 定位：**目标态设计**，不受当前实现约束；第 10 章给出从现状到目标的演进映射。
> 业内参照：Snowflake Cortex Analyst（Semantic Model + Verified Query Repository）、
> Databricks Genie（Instructions + Trusted Assets）、dbt MetricFlow / LookML（语义层）、
> Zep/Graphiti（双时态知识图谱、事实失效、混合检索）、DataHub/Amundsen（认证徽章、血缘治理）。

---

## 0. 一句话

把 ChatBI 所需的全部知识收敛为**一套统一资产模型**（六类资产 × 一个信任生命周期 × 双时态有效期），
存储在 Postgres + pgvector；召回收敛为**一条四阶段管道**（过滤 → 混合召回 → 重排 → 预算编译），
每条知识按信任档决定**应用语义**（Bind / Reuse / Exemplify / Constrain / Hint），
并由**反馈闭环**（信号 → 分诊队列 → 升格建议）持续沉淀。

---

## 1. 场景与需求盘点

我们的使用场景决定了知识体系必须满足：

| 场景 | 对知识体系的要求 |
|------|------------------|
| NL→SQL 生成 | 表/字段语义、join 路径、指标口径必须准确注入，且受 prompt 预算约束 |
| 澄清交互 | 澄清答案是最高价值的知识来源；沉淀后同类问题不再重复问 |
| 多工作区/多数据源 | 知识必须有 scope（oid / ds / assistant / user），不可跨界泄漏 |
| 高基数实体（地区、产品名等） | 需要专门的实体值索引，LLM 不能猜字面量（Cortex Search 模式） |
| Schema 演进 | 字段删改必须让引用它的知识**即时失效**，不能靠人肉排查 |
| 审计合规 | 任一条知识可回答"从哪来、谁认证、什么时候生效/失效、被哪些回答用过" |
| 运营治理 | 管理员有一个统一的待办队列（分诊、认证、升降格），而不是散落各处 |

**反需求（明确不做）：**

- 不引入图数据库（Neo4j 等）。Graphiti 的核心价值是双时态 + 事实失效 + 混合检索，
  这三件事在 Postgres 上都能做；我们的"图"（join 关系）本来就是结构化表。
- 不做用户级长期记忆/个性化画像（当前产品不需要，留扩展点即可）。
- 不做第二套执行审计（继续用 ChatLog）。
- 不在问数现场同步挖矿（沉淀永远异步，不阻塞回答）。

## 2. 知识分类：六类资产

业内共识是把"给 NL2SQL 的知识"分成**结构、语义、实体、范例、规则、情景**六层。
每层的产生方式、信任来源、应用方式都不同，**不能混在一张表里用一个召回策略**。

| # | 资产类 | 内容 | 业内对应 | 主要来源 | 应用语义 |
|---|--------|------|----------|----------|----------|
| K1 | **Structural** 结构 | 表/字段/类型/join 路径/画像统计 | Cortex semantic model 的 tables/relationships | DB 同步 + 画像挖掘 + DDL | 注入 schema prompt；join 只用已确认 |
| K2 | **Semantic** 口径 | 指标定义、维度口径、业务规则表达为契约片段 | MetricFlow metrics / Genie instructions | 澄清沉淀、显式保存、运营录入 | 认证后 **Bind**（结构化预填），否则 Constrain/Hint |
| K3 | **Entity** 实体 | 术语、同义词、维度值字典、高基数实体索引 | Cortex Search / dict | 字典生成、澄清选中、运营 | 归一化用户词 → 字段/值；不进硬 SQL 前先发布 |
| K4 | **Exemplar** 范例 | 已验证的 问题→SQL 对 | **Verified Query Repository** | 用户点赞/显式保存/运营验证 | 近似命中→**Reuse**（跳过生成）；一般命中→Exemplify（few-shot） |
| K5 | **Rule** 约束 | 安全/口径类硬规则（"销售额一律含税""不查个人明细"） | Genie instructions（强约束型） | 运营录入 | Constrain（进 assess/generate 的系统约束区） |
| K6 | **Episodic** 情景 | 历史 turn 的处理轨迹（问题→契约→结局） | Zep episodes | 每次成功 turn 自动 | 只作为挖掘原料与运营参考，**永不直接进 prompt** |

关键取舍：

- **K4 Reuse 是业内验证过的最大准确率杠杆**（Cortex VQR：近似命中直接返回已验证 SQL，
  跳过 LLM 生成，`confidence.verified_query_used` 可观测）。我们目前只有 few-shot
  （data_training），缺"高置信直接复用"这一档。
- **K2 与 K4 分开**：口径是可组合的契约片段（跨问题复用），范例是端到端的整问复用。
  Cortex 把两者都放 semantic model；我们分开存但共用生命周期。
- **K6 是原料不是知识**：episodes 只喂给挖掘和运营分析，检索面永远不含它。

## 3. 统一资产模型（存储层）

### 3.1 资产信封（所有 K1–K5 共享的元数据）

每条知识资产，无论哪类，都带同一个"信封"：

```text
asset_envelope:
  # 身份
  asset_kind        # caliber | exemplar | entity | rule | relation | ...
  natural_key       # 语义指纹（去重/合并/幂等的依据）
  lineage_id        # 血缘根，跨版本不变
  version           # 单调递增；新版本 supersede 旧版本

  # 归属（scope，决定可见性，召回第一道过滤）
  oid               # 工作区，必填
  datasource_id     # 可空 = 工作区级通用知识
  assistant_id      # 可空
  scope_extra       # 预留（user 级等）

  # 信任（决定应用语义，见 §4）
  trust_tier        # staged | published | trusted | certified
  certified_by / certified_at

  # 双时态（Graphiti 模式）
  valid_from / valid_to      # 业务有效期；失效 = 置 valid_to，不删行
  created_at / updated_at    # 系统时间
  superseded_by              # 新版本指针

  # 依赖与失效
  schema_refs       # 引用的 (ds, table, field) 列表，规范化存储
  schema_fingerprint # 引用对象在采集时的指纹快照

  # 溯源（结构化、不向量化、可视化展示，见 §3.1-5 / §7.1）
  provenance        # 按来源类型的结构化溯源，准入时校验完整性
  evidence          # 证据包（复现次数、点赞数、来源快照）——只能服务端写
```

设计要点（对应业内经验）：

1. **双时态 + supersede 而非删除**（Graphiti/Zep）：知识被修正时旧版本置
   `valid_to` 并指向新版本；审计可回答"上月这个口径是什么"。所有查询默认
   `valid_to IS NULL AND enabled`。
2. **natural_key 是幂等锚点**：同一口径被澄清十次只产生一条资产 + 十条证据，
   证据累积驱动升格（而不是十条重复知识互相稀释召回）。
3. **schema_refs 规范化存储**（独立关联表，非 JSON 里埋着）：schema 同步发现字段
   删改时，一条 SQL 就能找出所有受影响资产并批量失效（L-1 联动的正确形态）。
4. **evidence 只能服务端写**：复现计数、使用计数来自系统事实（ChatLog / apply_log
   回填），API 永远不接受客户端上报的证据数字。
5. **溯源按来源类型结构化**，每类生产者有各自的必填字段，准入时校验，缺失即拒绝：

   | 来源 | provenance 必填 | 可点穿到 |
   |------|-----------------|----------|
   | 问答沉淀 | record_id、clarification_id、原始问题、用户答案摘录、触发器 ID | 原对话回放 |
   | 数据库挖掘 | scan_run_id、表/字段快照、挖掘策略与证据（样本行数、匹配率） | 扫描运行详情 |
   | 人工填写 | actor_user_id、录入时间、填写说明 | 操作者 |
   | 代码分析提取 | 仓库/文件/行号、代码片段快照、分析器版本 | 源码位置 |
   | 文档提取 | 文档 ID/版本、章节/页码定位、原文摘录、提取器版本 | 文档原文段落 |

   溯源信息**不参与向量化**（它回答"从哪来"，不参与"像不像"），但必须在
   控制台可视化展示并支持点穿（§7.1）。

### 3.2 物理存储

```text
Postgres（系统库）
├── knowledge_asset            # 信封 + payload(JSONB)，承载 K2 口径 / K4 范例 / K5 规则
├── knowledge_schema_ref       # asset_id → (ds, table, field)，失效联动用
├── knowledge_evidence         # 证据事件（append-only）：复现、点赞、apply 回填
├── knowledge_lineage_event    # 生命周期事件（append-only）：staged/published/certified/…
├── knowledge_staging          # 隔离区（未准入的候选，见 §5）
├── knowledge_episode          # K6 原料（独立表，永不进召回索引）
└── knowledge_index (pgvector) # 统一向量索引：asset_id + kind + scope + embedding
                               #  + tsvector（BM25 近似，pg 原生全文检索）
                               #  + embedding_fingerprint（内容指纹，防重复嵌入）
```

各资产类的落表归属（避免双写）：

- **K2/K4/K5 → `knowledge_asset`**：单表多态，信封 + 类内 payload。
- **K1 结构知识不搬家**：表/字段/关系继续用 `core_table/core_field/field_relation`
  与 CONFIRMED 治理；资产模型只为它记 lineage 事件，不重复存储。
- **K3 实体不搬家**：terminology / dictionary 的既有表与发布代机制保留，补齐
  信封字段（lineage_id、溯源），接入统一 lineage 事件，召回统一走 compile 门面。
- **K6 只落 `knowledge_episode`**：不建嵌入、不进检索面，仅供挖掘与运营分析读取。
- **统一向量索引而非每类一套**：kind + scope 建复合索引；一次嵌入调用可以服务
  排序与召回两个用途，但**嵌入文本按用途分离**（RANK 文本 ≠ PROMPT 文本，延续
  现有原则）。
- **不引入独立向量库**（Milvus 等）：数据量级（每工作区万级知识）pgvector 足够，
  少一个运维面。

### 3.3 K4 范例的特殊字段（VQR 模式）

```text
exemplar payload:
  question_norm      # 归一化问题
  sql                # 已验证 SQL（引用逻辑名，见下）
  contract_snapshot  # 当时的查询契约（可选，用于结构化比对）
  verified_by / verified_at
  reuse_threshold    # 相似度 ≥ 此值可直接 Reuse（默认全局配置）
  dialect / ds_id    # 方言绑定
```

Cortex 的一个关键细节值得抄：**verified SQL 引用语义模型的逻辑名而非物理列名**。
我们的对应做法：范例 SQL 存储时把表/字段落到 `schema_refs`，物理重命名时可判定
失效；Reuse 前做一次轻量校验（引用的字段仍存在 + 方言匹配），失败则降级为 Exemplify。

### 3.4 可读资产为本，向量为衍生索引（可读性与同步机制）

业内的标准答案就是"**可读的事实源 + 派生的检索索引**"（Cortex 的 semantic model
是人可读可维护的 YAML，全部检索索引由它派生），没有更好的替代——关键是把它
做严格：

1. **可读资产是唯一事实源**。人维护的永远是结构化 payload 与可读文本
   （口径的契约片段 + 描述、范例的问题 + SQL、术语与同义词）；
   `knowledge_index` 里的 embedding / tsvector 是**衍生数据**，可随时从资产
   全量重建，损毁不丢知识。
2. **所见即所嵌（投影函数）**。RANK 嵌入文本、PROMPT 注入文本都由**确定性模板**
   从同一份 payload 渲染（延续 RANK≠PROMPT：两个模板，一个源）。控制台展示的
   "嵌入预览"就是模板输出——运营在 UI 里改的内容，就是将要被嵌入的内容，
   不存在第二份需要人对齐的"向量侧文案"。
3. **指纹驱动的同步**（沿用现有 embedding_fingerprint 模式）：资产保存事务内
   重算内容指纹，指纹变化 → 标记索引行 stale，异步 worker 重嵌；指纹不变
   （如只改溯源备注）不重嵌。supersede 产生新版本 → 新行重嵌，旧行随资产
   失效被过滤。
4. **索引过期永不脏读**。召回结果**必须回表 join 资产状态**
   （enabled / valid_to / trust_tier 以资产表为准）：向量行落后最多损失一点
   召回率，绝不会让已禁用/已失效的知识复活。禁用生效 = 一次 UPDATE，
   不等重嵌。
5. **不向量化的字段明确列出**：provenance、evidence、lineage、schema_refs——
   它们回答"从哪来、可不可信"，不参与"像不像"，只做可视化展示（§7.1）。

## 4. 信任生命周期（治理层）

四档信任 + 明确的升降格规则，应用语义由信任档**硬编码**（不许调用方绕过）：

```text
staged ──(准入检查)──► published ──(证据达标)──► trusted ──(人工认证)──► certified
   │                      │                        │                       │
   └── 拒绝/过期          └────────── 漂移/降格/禁用（即时生效）◄───────────┘
```

| trust_tier | K2 口径 | K4 范例 | K3 实体 | K5 规则 |
|------------|---------|---------|---------|---------|
| staged | 不召回 | 不召回 | 不召回 | 不适用（规则生来是人工的） |
| published | Hint（弱提示，可关） | Exemplify | 发布代可用 | Constrain |
| trusted | Constrain | 加权 Exemplify | — | Constrain |
| certified | **Bind** | **Reuse**（近似命中直接复用） | — | Constrain |

升格规则（服务端证据，不接受申报）：

- `published → trusted`：evidence 中服务端记录的复现次数 ≥ N（默认 2），或点赞 ≥ M。
  复现 = 同 natural_key 的知识在**不同 turn** 被 apply 且该 turn outcome 成功。
- `trusted → certified`：**只能人工**。运营在分诊队列里看证据包（来源对话、
  复现列表、引用字段现状）后签发。Bind 和 Reuse 是强干预，必须有人负责。
- 降格/禁用：即时生效（enabled=false 或 valid_to=now），不需要审批。宁可漏用不可错用。

漂移失效（L-1 的目标形态）：

- schema 同步事务内，diff 出删除/改型的字段 → 按 `knowledge_schema_ref` 找到所有
  引用资产 → 置 `enabled=false` + lineage 记 `schema_invalidated` 事件 → 出现在
  分诊队列等人处理（修复或废弃）。
- 数据源删除 → 该 scope 全部知识级联失效。

## 5. 沉淀管道（写入侧）

```text
turn 结束（异步，不阻塞回答）
  │
  ├─ K6: 无条件落 episode（成功/降级/失败都落，失败是负样本原料）
  │
  ├─ 触发器矩阵（V-T*）判定 → 产出候选
  │     V-T1 澄清链成功    → K2 口径候选（仅 user:answer 子句）+ K3 实体候选
  │     V-T2 点赞/收藏     → K4 范例候选（question+SQL+契约快照）
  │     V-T3 显式"保存为口径/范例" → 对应候选，高优先级
  │     V-T4 高频相似问题   → K4 范例建议（Cortex "Verified Query Suggestion" 模式）
  │
  ├─ 准入检查（进 staging 前，机器把关）：
  │     schema 校验（引用字段存在且 READY）
  │     字面量清洗（订单号/UUID/时间戳等瞬时值 → 参数化或拒绝）
  │     scope 完整（oid/ds 必须齐）
  │     溯源完整（按来源类型校验 §3.1-5 必填字段；无法点穿到来源的候选拒绝）
  │     natural_key 计算 → 已有同 key 资产则转为"证据累积"而非新候选
  │
  ├─ knowledge_staging（隔离区，pending）
  │
  └─ 分诊队列（运营界面）：
        approve → published（K2/K4）或 dict staging（K3，仍走字典发布流程）
        reject  → rejected + 原因（原因回流为清洗规则的训练素材）
        过期未处理 → expired 自动清理（默认 30 天）
```

关键设计：

1. **证据累积优先于新建**。同一口径第二次被澄清确认，正确动作是给已有资产
   `+1 复现证据`（可能触发 trusted 升格建议），而不是再进一条 staging。这是
   natural_key 存在的核心理由。
2. **失败也采集**（只进 K6）。Cortex 的运营模式是"把负反馈接进分诊队列，每周
   补 3–5 条 verified query"——负样本告诉运营该补哪条知识，比正样本更值钱。
3. **每一步写 lineage 事件**（同事务）。staging 准入、approve、publish、升格、
   失效各一条，事件引用 record_id / clarification_id / actor，审计可点穿到原对话。
4. **人工录入走同一契约，但有快速通道**。运营/管理员录入（含 K5 规则）同样经
   submit_candidate 与 lineage 记录；当操作者本身具备治理权限时，准入即发布
   （staging 自动通过，事件照记）。契约统一是为了溯源与红线一致，不是为了
   让作者审批自己。certified 档仍不例外——Bind/Reuse 必须显式签发。

## 6. 召回管道（读取侧）

四阶段，所有资产类共用骨架，参数按 kind × stage 配置：

```text
compile_knowledge(question, stage, scope) →

① Scope & Trust 过滤（SQL WHERE，非启发式）
     oid + ds + assistant 匹配；valid_to IS NULL；enabled；
     trust_tier ≥ 该 kind 在该 stage 的最低档

② 混合候选生成（Hybrid，Graphiti/业内共识）
     向量召回（pgvector cosine，RANK 用途嵌入）
     ∪ 词法召回（pg tsvector / trigram，处理专有名词与中文分词盲区）
     ∪ 结构化命中（K3 实体：用户词精确/前缀命中字典；K2：契约槽位字段匹配）
     每路取 top-k，合并去重

③ 重排（可选，按价值开）
     K4 范例：相似度 ≥ reuse_threshold 且 certified → 标记 Reuse 短路
     其余：轻量打分 = 相似度 × 信任权重 × 新鲜度 × 历史 apply 成功率
     （先不上 cross-encoder；打分特征都来自服务端事实，成本为零）

④ 预算编译（Compile）
     按 stage 分配 token 预算（assess / generate / chart 各自独立）
     按应用语义装配：
       Bind      → 结构化写入契约草稿（不占 prompt 预算）
       Reuse     → 直接返回已验证 SQL，跳过生成（K4 certified 近似命中）
       Constrain → 系统约束区（K5 + trusted K2）
       Exemplify → few-shot 区（K4 published+）
       Hint      → 剩余预算内的弱提示
     产出 apply_log：每条被应用知识记 {asset_id, lineage_id, tier, apply, reason}
```

设计要点：

1. **Reuse 短路是新增的最高档**：certified 范例近似命中时直接复用 SQL（做完
   §3.3 的轻量校验），响应快且确定性高；`apply=reuse` 记入 ChatLog，前端可展示
   "本回答复用了已验证查询"。这是对标 VQR 的核心收益点。执行细则：
   - **位置**：判定在 assess 完成后、generate 之前——契约槽位已归一，骨架
     匹配才可用；不在 assess 前抢跑（澄清逻辑不能被绕过）。
   - **字面量重绑**：命中要求骨架一致 **且** 范例 SQL 中的全部字面量槽都能从
     当前契约槽位重绑定（谓词值经 K3 字典解析、时间经确定性解析器）；任一
     槽位无法重绑 → 降级 Exemplify，绝不带着旧字面量照搬。
   - **安全不变**：复用的 SQL 仍走既有行列权限注入与执行管道，只复用 SQL
     文本，不缓存执行结果。
   - **缓存回表**：热点缓存只存"归一问题 → asset_id"映射，命中后仍回表校验
     资产状态（§3.4-4），禁用/失效即时切断。
2. **Bind 的冲突语义必须严格**：Bind 只能填空槽或与用户证据一致的槽；与用户
   当轮表述冲突 → 转 clarify（把口径作为候选项展示），**绝不静默覆盖，也绝不
   把 knowledge 证据盖到非知识值上**。用户证据 > certified 知识，永远。
3. **词法召回不是可选项**：业务口径里全是专有名词（"签收额"“GMV口径A"），
   纯向量对这类短语常常失灵；pg 原生 tsvector+trigram 成本极低。
4. **预算是一等公民**（Cortex 的 32K token 上限教训）：schema 大时知识必须竞争
   排队，编译器负责裁剪并在 apply_log 里记录"因预算被裁掉的知识"，可观测。
5. **stage 路由**：assess 只要 K2/K3/K5（帮助理解意图），generate 要 K1/K4/K5
   （帮助写对 SQL），chart 基本不要知识。不做一次召回全 stage 复用。

### 6.1 NL2SQL 场景特化召回

NL2SQL 区别于通用 RAG 的本质：问题最终一定落到 schema 和查询契约上，
这两个结构化锚点让召回不必依赖整句文本相似度。按价值排序：

1. **契约槽位驱动召回**（最大精度杠杆）。assess 产出的契约草稿中，缺失/模糊的
   槽位本身就是最精确的召回查询：指标槽模糊 → 只召回该词命中的 K2 口径；
   谓词字面量未解析 → 只走 K3 字典精确/前缀通道；时间槽 → 确定性时间解析器，
   **不召回**（时间表达交给规则比交给检索可靠）。用槽位而非整句去查，
   精度上升、预算下降。
2. **Schema 锚定的二跳召回**。先 schema linking（问题 → 候选表/字段），再以命中
   字段为键走 `knowledge_schema_ref` 的结构化 join 召回绑定知识；反向同样成立
   ——字典字面量命中反推字段归属，本身就是 schema linking 证据。配合 CONFIRMED
   join 图做可达性剪枝，schema prompt 与知识召回同时收窄。
3. **范例骨架匹配**（DAIL-SQL 系结论）。范例选择用掩码归一问题
   （"上个月华东的签收额" → "{时间}{地区}的{指标}"）+ SQL 骨架相似度
   （聚合/分组/TopN 结构），而非原句向量。契约槽位标注天然是掩码依据，
   不需要额外模型。这是 Reuse 短路敢开高阈值的前置条件。
4. **重排特征用执行事实**。apply 后执行成功率、与锚点表共现频率、复用历史——
   全部来自 ChatLog 事实，零推理成本，优先于任何 cross-encoder。
5. **热点问题缓存**。BI 问题重复度极高（日报式提问、固定口径）；归一化问题做
   命中缓存直接映射 certified 范例 → Reuse，这层命中率可能高于全部语义召回。
6. **方言/数据源硬分区**。`ds_id + dialect` 永远是 SQL 级前置过滤，跨方言范例
   是负资产。

落位：#1、#2 归 M1/M2（`knowledge_schema_ref` 建好后 #2 是一条 SQL 的事）；
#3 与 M2 的 Reuse 短路绑定实施；#4、#5 归 M3。

## 7. 反馈闭环（运营层）

```text
信号采集（全部服务端事实）
  点赞/点踩 · 显式保存 · Reuse/Bind 后的执行结局 · 同口径复现 · 高频问题聚类
        │
        ▼
分诊队列（单一运营入口）
  待准入的 staging · 升格建议（证据达标）· 漂移失效待处理 · 负反馈待补知识
        │
        ▼
运营动作 → lineage 事件 → 知识库更新 → 下一轮召回即生效
```

- **采集点**：apply_outcome / usage 信号由 NLQ 在 turn 结束后与沉淀作业同批
  异步上报（emit_signal），不阻塞回答；点赞/点踩按该回答 apply_log 里的资产
  归因，并按应用语义加权（Bind/Reuse 强归因、Hint 弱归因），避免一次点赞
  给十条弱提示知识同时记功。
- **一个队列**，不是每类资产一个页面。运营每天打开一处，按优先级处理。
- 升格**建议**由系统算（证据达标自动进队列），升格**动作**由人签发（certified 档）。
- 被 Bind/Reuse 的知识若导致执行失败或用户点踩，自动生成"复核"队列项并可
  一键临时降档——错误知识的止血通道必须比生效通道更快。

### 7.1 知识控制台（可视化维护与交互设计）

知识库的可维护性取决于控制台，控制台展示的永远是**可读资产 + 溯源 + 证据**
（§3.4：向量不可读也不需要被看见）。三个核心界面：

**① 资产详情页**——一条知识的全部真相，四个分区：

| 分区 | 内容 | 交互 |
|------|------|------|
| 内容 | 可读 payload（口径的契约片段+描述 / 范例的问题+SQL / 术语同义词），附"嵌入预览"（投影模板输出，所见即所嵌） | 就地编辑 → 自动产生新版本 + supersede + 按指纹重嵌，无"静默改库" |
| 溯源 | 按 §3.1-5 的结构化溯源渲染：来源类型徽章 + 原文摘录 + **点穿链接**（原对话回放 / 文档段落 / 源码行 / 扫描详情） | 只读；点穿跳转 |
| 血缘与证据 | lineage 时间线（staged→published→certified→…，每个节点带操作者与证据包快照）；服务端证据面板（复现列表、apply 成功率、点赞数） | 时间线节点可展开证据快照 |
| 健康度 | schema_refs 现状（引用字段是否仍存在/READY）、where-used（近期命中的回答列表）、命中/预算裁剪统计 | 异常置顶红色提示 |

**② 分诊队列**——运营唯一工作台，卡片式逐条处理：

- 一张卡片一屏内给全决策信息：候选可读内容、来源摘录（澄清原文/文档原文）、
  **与相似已有资产的 diff**（natural_key 邻近项，防重复入库）、建议动作。
- 动作一键化：approve / reject（必填原因，回流为清洗规则素材）/
  合并为已有资产的证据 / 编辑后通过。
- 队列分区按优先级：显式保存 > 升格建议 > 澄清沉淀 > 漂移失效待处理 > 负反馈。

**③ 影响面预览与回答侧联动**：

- certify / disable 前展示影响面：该知识将命中哪些历史问题（用归一化问题
  离线回放估算）。目标态下 Bind/Reuse 类操作过这一步——强干预要先看后果；
  落地节奏见 §10（M3，视运营量决定）。
- 聊天回答侧展示"本回答使用的知识"（来自 apply_log），点击直达资产详情页；
  用户点踩时该链路反向生成复核队列项。这是运营发现坏知识的最短路径。
- 信任档全站统一视觉：certified 徽章（对标 DataHub 认证徽章）、trusted、
  published、staged 灰显，让"这条知识多可信"在任何列表一眼可辨。

交互红线：**所有 UI 编辑走域 API（§9），产生 lineage 事件与新版本**；
控制台没有任何直改数据库的后门。

## 8. 可观测与审计

沿用单一审计通道原则：

- **应用侧**：apply_log 进 ChatLog span meta（现有 `knowledge_apply` 扩展），
  字段固定为 `{asset_id, lineage_id, trust_tier, apply, reason}`。回答页可展开
  "本回答用了哪些知识"。
- **资产侧**：`knowledge_lineage_event` append-only，一条知识的完整历史 =
  一次查询。事件必须带 evidence_snapshot（认证时看到的证据包快照）。
- **两侧互指**：apply_log 带 lineage_id，lineage 事件带 record_id，双向可点穿。
- 核心指标（运营看板）：各档资产数、staging 积压、Reuse/Bind 命中率、
  被 Bind 后的成功率 vs 无知识基线、漂移失效待处理数。

## 9. 边界与标准接口：知识平面的解耦

知识体系应当是一个**相对独立的域（Knowledge Plane）**，与外部只通过三个稳定契约
交互。边界形态是**进程内域边界 + 版本化 DTO**，不是微服务——拆服务解决的是
部署问题，我们要解决的是依赖方向问题。

### 9.1 为什么现在定边界

- 生产者即将从 2 个（挖掘、澄清沉淀）涨到 5+（人工、代码分析、文档提取）。
  没有写入契约，每接一个源就要在核心里开一条私有路径。
- 消费者当前只有 NLQ，但 config assistant、开放 API、MCP 都在路上。
  没有消费契约，信任规则会被每个消费者各自"理解"一遍。
- 升格/失效逻辑一旦散进 Catalog 同步、chat 节点等外部代码，信任不变式
  （§11）就无法在一个地方被证明。

### 9.2 三个契约

**① 写入契约 `submit_candidate`（生产者 → 域）**

```text
submit_candidate(KnowledgeCandidate) -> CandidateReceipt

KnowledgeCandidate:
  kind, payload            # 资产类 + 类内载荷
  scope                    # oid / ds / assistant
  provenance               # 谁、从哪个对话/文档/扫描发现的
  suggested_tier           # 仅是建议，域内可无视
  evidence_hints           # 线索（如来源快照），不是证据数字
```

全部生产者——数据库挖掘、人工填写、问答沉淀、代码分析提取、业务文档提取——
走同一入口。域内统一负责：准入校验（schema/清洗/scope）、natural_key 去重
（已存在 → 转证据累积）、staging 隔离。

红线：**生产者不写资产表、不写 lineage、不指定最终信任档。**
生产者的职责到"发现并投递"为止；新增一个知识源应当是纯增量，核心零改动。

**② 信号契约 `emit_signal`（外部事实 → 治理）**

```text
emit_signal(KnowledgeSignal)
  kind: apply_outcome      # 某资产被应用后该 turn 的执行结局
      | user_feedback      # 点赞/点踩/显式保存
      | schema_drift       # Catalog 同步发现引用对象变更
      | usage              # 复现/命中计数事实
  refs: {asset_id? natural_key? schema_ref? record_id?}
  fact: {...}              # 纯事实描述，不含动作指令
```

外部**只报事实，不下指令**。升格、降格、失效的决策规则全部在域内：
Catalog 同步不再直接改知识表，而是发 `schema_drift` 信号，由域内按
`knowledge_schema_ref` 执行失效；ChatLog 证据回填也走这里。
这样 §4 的全部升降格规则可以在一个模块内被完整审计和测试。

**③ 消费契约 `compile_knowledge`（域 → 消费者）**

```text
compile_knowledge(CompileRequest) -> KnowledgeBundle

CompileRequest:  question, stage, scope, contract_slots?, budget?
KnowledgeBundle: reuse? | bound[] | constraints[] | exemplars[] | hints[]
                 + apply_log[]        # 每条含 asset_id/lineage_id/tier/apply/reason
                 + bundle_version
```

消费者（NLQ graph、config assistant、未来开放 API）只按应用语义装配，
不感知存储结构、检索策略、信任规则。Bundle 是版本化 DTO；召回失败/超时
降级为空 bundle（裸跑），永不阻塞回答。

红线：**任何模块不得绕过 compile 直查知识表。**现有旁路
（`dictionary_recall`、`match_training` 直连、nlq 内直接操作 bind 合并）
逐步收编为 compile 的内部实现或 Bundle 的装配助手。

### 9.3 边界的执行手段

契约不靠自觉，靠机制：

1. **包边界**：`apps/knowledge` 只从门面模块（如 `apps/knowledge/gateway.py`）
   导出这三个入口 + 治理 API（staging/certify/分诊队列）；`capture/ staging/
   assets/ retrieval/ compile/ lineage/` 均为域内私有，外部 import 视为缺陷。
2. **写权限约定**：`knowledge_*` 表只由域内代码写。用一条 import 检查测试
   守住（断言外部模块不 import 域内私有模块），不引入额外工具也能跑。
3. **治理界面属于域**：分诊队列、认证、升降格的 API/UI 都是域的一部分，
   其他业务模块不提供第二个知识管理入口。

### 9.4 明确不做

- 不拆微服务、不独立数据库——进程内调用 + 同库事务是优势不是债务。
- 不上消息队列——`submit_candidate` 异步化用现有 capture job 表即可。
- 不做生产者插件注册框架——生产者就是"调一个函数"，五个源不需要框架。
- 契约就三个，不为假想的消费者预留第四个。

## 10. 与现状的映射与演进路线

现有实现大部分是这套目标架构的正确子集，演进而非重写：

| 现有 | 目标态归宿 |
|------|-----------|
| `business_caliber` + `knowledge_staging` + lineage | K2 主体已在；补 natural_key 证据累积、双时态字段、schema_ref 规范化表 |
| `data_training`（few-shot） | 升级为 K4：加 verified 元数据 + reuse_threshold + certified 档 → 补 Reuse 短路 |
| `terminology` / `dictionary` | K3 主体已在；澄清选中 → dict staging 的 L-2 链路补完 |
| `core_table/field/relation` + profiling | K1 不动；纳入统一 lineage 事件 + schema_ref 失效联动 |
| （无） | K5 规则：新增，最简单的一类（纯人工录入 + Constrain 注入） |
| `process_episode` | 收敛为 K6：降回原料定位，去掉 published 直写，不建 provider |
| `compile_knowledge_for_turn` | 保留为管道骨架；补词法召回、Reuse 短路、预算裁剪记录 |
| `promote-trusted` API | 改造：删客户端计数，改为服务端证据 + 建议队列 |

分期（每期独立可验收）：

- **M1 止血 + 地基**：修 Bind 冲突/`values` 缺陷；evidence 服务端化（废客户端
  reproduce_count）；`knowledge_schema_ref` 表 + 同步失效联动；staging 准入检查
  （schema 校验 + 字面量清洗）；**三契约门面成形**（submit / signal / compile，
  §9），现有生产者与消费旁路收编到门面之后。
- **M2 最大杠杆**：K4 升级为 VQR 模式（verified 元数据、certified 档、Reuse 短路
  + 字面量重绑校验）；点赞/显式保存 → 范例候选；分诊队列 API + 最小 UI；
  回答侧"本回答使用的知识"展示。
- **M3 闭环完善**：natural_key 证据累积与复现升格；词法召回补路；负反馈 →
  待补知识队列；运营看板指标；L-2 实体→dict 链路补完；资产详情页
  （溯源/血缘/健康度）；影响面预览（可选，视运营量再决定）。

**每期都不做的**：图数据库、独立向量库、cross-encoder 重排、用户级记忆、
Process provider 进 prompt、双时态的"任意时间点查询" UI（先只存不查）。

## 11. 不变式清单（实现红线）

1. staged / 未发布代 / CANDIDATE 永不进入任何 prompt 或结构化预填。
2. Bind 与 Reuse 只允许 certified；certified 只能人工签发。
3. 用户当轮证据 > 任何知识；冲突 → clarify，不静默覆盖，不伪造 evidence。
4. 所有证据数字（复现、使用、点赞）只由服务端从事实回填。
5. schema 漂移 → 引用资产即时失效，先失效后人审。
6. 知识失效用 valid_to / supersede，不物理删除；lineage append-only。
7. 应用必留痕：无 apply_log 的知识注入是缺陷。
8. 沉淀异步、失败不影响回答；召回超时降级为"无知识裸跑"。
9. 生产者只投递候选（submit_candidate），不写资产表/lineage、不定信任档。
10. 消费只经 compile_knowledge 门面，任何模块不绕过它直查知识表。
11. 可读资产是唯一事实源；向量/tsvector 是可全量重建的衍生索引，召回结果
    必须回表校验资产状态（禁用/失效即时生效，不等重嵌）。
12. 无完整结构化溯源（按来源类型必填、可点穿）的候选不得准入；溯源不向量化，
    但必须可视化展示。
