# Wiki 知识体系总体方案（数据问数版）

> 定位：以 llm-wiki 已验证实现为基座，面向 **NL2SQL（数据问数）** 的知识体系全链路方案。
> 本文回答三个问题：与 llm-wiki 的横向比对结论；提取的 wiki 如何**确保**达成问数预期效果；完整流程。
> 关联：页面契约 `docs/wiki页面契约-spec-v0.md` · 源码摄取 `docs/wiki-knowledge/wiki源码摄取适配器-v1.md` · 召回 `docs/wiki-knowledge/wiki召回接口-v1.md`

---

## 一、根本差异：消费者不同，质量定义不同

| 维度 | llm-wiki | 我们（数据问数） | 对方案的约束 |
|---|---|---|---|
| 消费者 | 人 + 通用 LLM agent（读页综合，容忍散文） | **SQL 规划器 + 确定性门禁**（错误直接变成错误数据） | 页面必须携带**机器可验证的锚点**，散文只是辅助 |
| 源 | 文档/PDF/网页（叙述性、自包含） | **业务系统源码 + DB schema + 历史查询**（与库强耦合、会漂移） | 必须有确定性扫描器打底 + schema 指纹增量 + coverage 闭环 |
| 质量定义 | 人读起来对、链接丰富 | **可机械验收**：枚举映射可对账、口径谓词可对比、关系可回验 | 每类页面绑定验收标准（见 §三） |
| 问答方式 | 检索 → LLM 读页综合 → 人判断 | 检索 → 文本直拼 prompt → 规划器 → **门禁验证** → 执行 | 确定性边界在门禁不在知识（已定架构） |
| 漂移 | 源文档基本不变 | **DDL/代码持续变更** | schema 指纹驱动 stale lint → 增量重摄取 |

一句话：llm-wiki 的页面是"给人读的知识"，我们的页面是"给规划器用的语义契约 + 给人审的载体"。**锚点块是两者的合金**：散文区服务人审与业务语义召回，锚点块服务机器验收与确定性消费。

### 2.2 舍（llm-wiki 有而问数不需要）

多模态图片摄取与 caption、Deep Research/Web 搜索、Marp/Canvas 输出格式、通用聊天 agent 运行时（我们的消费者是确定性管道）、Obsidian 生态依赖（管理界面自建轻量版）、查询时 LLM 自由读页（运行时只拼文本，已定）。

## 三、效果保证：失败模式 → 页面类型 → 提取源 → 验收标准

"确保达成预期效果"的可操作定义：**每类真实失败模式都有对应的页面类型、明确的提取来源、和可机械验收的标准**。

| # | 问数失败模式 | 页面类型（锚点） | 提取来源 | 验收标准（机械可测） |
|---|---|---|---|---|
| F1 | 枚举值↔业务术语鸿沟（"平台录入"→?） | `enum` 页 + `concept` 术语桥 | 底稿.enums + 枚举类/字典注释 + service 语义 | 评测题命中率；`ENUM_NOT_IN_BASELINE` 零漏网；术语桥 `maps_to` 对账底稿 |
| F2 | 状态谓词错误（create_time 顶替业务状态） | `process` 页（状态机+读写效果） | service 状态机代码 + 底稿 | 语义复核阶段：谓词字段 ∈ process.effects 声明字段 |
| F3 | 口径不一致/静默选边 | `caliber` 页 | mapper WHERE 提取 + 文档 | pattern/caliber 自洽校验（`PATTERN_CALIBER_MISMATCH`）；SQL WHERE 与 filters 对比 |
| F4 | JOIN 猜测（o.name 幻觉列） | `table` 页 `ground:relation` | 底稿.relationships（mapper join/FK） | 关系端点对账底稿；租户字段端点零容忍 |
| F5 | SQL 范式/方言（CTE 不兼容） | `pattern` 页（question+sql+calibers） | 历史成功 SQL 回填 + 修复案例 | `verification` 状态门禁；回填页 REVIEW 通过率 |
| F6 | 表/字段不可见 | `table` 页 + 既有地图/值索引 | 底稿.catalog | `COVERAGE_GAP`：活跃表覆盖率 |
| F7 | 多表场景选错主表 | `scenario` 闭包页 | 域模型 + 人工 | 场景题集命中 |

**验收基座**：`scripts/knowledge_recall_eval.py` 题集双跑（wiki 召回 vs unit 基线），指标 = 表召回@k / 枚举映射命中率 / 口径谓词正确率 / 澄清率下降幅度；单域端到端试点选**企业建档域**（同时覆盖 F1-F4，是最难样本）。

## 四、完整流程

### 4.1 全链路

```
┌─ 提取（Spec B）────────────────────────────────────────────┐
│ 业务仓库 → 确定性扫描器（catalog/enums/relationships 底稿）    │
│          → scope 切片（表/域）→ Step1 LLM 结构化分析          │
│          → Step2 生成页面（散文+锚点块+wikilinks+REVIEW 块）   │
│          → sanitize 白名单 → groundExtract/Validate（丢块+警告）│
│          → 锚点对账底稿（幻觉拦截）→ 类型目录路由 → 写入        │
├─ 存储 ────────────────────────────────────────────────────┤
│ 验证期：git 页面目录（llm_wiki 项目）；产品化：阶段二服务化      │
├─ 管理 ────────────────────────────────────────────────────┤
│ REVIEW 队列（预置动作）+ 持续 lint（矛盾/过期/孤页/缺页/覆盖）   │
│ + schema 指纹增量重摄取 + 三路/确定性合并 + 人工发布门禁        │
├─ 召回（Spec C，backend/apps/knowledge/wiki/）──────────────┤
│ load_dir → 切块（锚点围栏原子）→ 嵌入(指纹失效) → RRF         │
│ → 页面聚合 → 图扩展配额 → RenderedPassage（文本直拼）          │
│   business 阶段：业务语义背景 + 业务澄清（图配额全开）           │
│   physical 阶段：门禁 missing_concepts 检索（降格候选竞争）     │
├─ 消费 ────────────────────────────────────────────────────┤
│ <business_knowledge>/<business_rules> 段 → 规划器             │
│ → 门禁（missing_concepts 反弹 / T4 扩表 / 重校验）→ 执行        │
├─ 回填 ────────────────────────────────────────────────────┤
│ 澄清结论（"平台录入"=AGW_BUILD）/ 好答案 → 候选页（pending 源）  │
│ → 两步 ingest → 三层合并 → REVIEW → 发布（闭环，复用 clip 通道）│
└──────────────────────────────────────────────────────────┘
```

### 4.2 运行时轮次视图（问数一轮的生命线）

```
问题 → turn_router → 值索引/地图/知识绑定（不变）
    → retrieve_context：wiki.recall(business) 拼业务语义段
    → [命中充分] 规划（枚举映射/口径/状态谓词有据）→ ready
    → [缺口] missing_concepts → 门禁 wiki.recall(physical) → 反弹一次
    → SQL → 硬门禁（含关系真值校验）→ 修复 → 执行
    → 澄清结论/好结论 → 回填候选（下一轮的知识养分）
```
