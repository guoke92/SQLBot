## 0. 消费者与成功标准

问数 Wiki 的消费者是 **SQL 规划器 + 确定性门禁**，不是「读页综合的人」。

一次用户问题必须能完成这六件事，缺一则链路未闭环：

| # | 工作 | 契约落点 |
|---|---|---|
| 1 | 说法 → 物理键 | `concept` / `aliases` 绑 `表.字段` 或 `dictKey.VALUE` |
| 2 | 值怎么存、怎么叫 | 表字段 `dictionary` + 枚举页；label 只跟代码 |
| 3 | 命名集合 → 可执行谓词 | 少量高复用 `caliber`（禁止一值一口径） |
| 4 | 合法 JOIN | `ground:relation`：EQUI_JOIN / SHARED_KEY / DERIVED + 证据 |
| 5 | 默认过滤 / 软删 / 有效 | `rule` 或 caliber，规划约束不是散文建议 |
| 6 | 好答案复利 | 澄清 / 成功 SQL → 同管道 REVIEW → `pattern`/`query` |

业内对照（只取对问数有用的）：Looker/dbt/Cube 的 **certified semantic layer**（实体、认证 JOIN、指标/过滤、同义词）= 我们的 wiki ground；BIRD/Spider 的主因是 **schema linking 错表不可恢复** → 场景窗裁剪 + 列全集在页、投影进 prompt；Karpathy LLM Wiki 的 **compile once, query compounds** → 问答时不重推源码；CHESS/C3 的值召回 → 枚举/profile **编译进 wiki**，不是问数时扫 catalog；Vanna 的 certified SQL → `pattern` 页。不取：查询时 LLM 自由翻仓库、一值一口径、unit/semantic 双轨、把 RAG 打在生 DDL 上。

## 1. 两层真相（禁止混用）

| 层 | 权威 | 禁止 |
|---|---|---|
| **编译期** | DB catalog = 存在性 / 类型 / 可空；代码 = label、JOIN、生命周期；profile = topk/分布 | LLM 脑补列、脑补 label、脑补 From→To |
| **运行期（已绑定语料）** | **只读 published wiki**。表页 = 该表列全集。场景窗 = 代码证实的用法划分 | 缺列就回退 catalog；缺表页就 `db catalog` 直渲进 prompt |
| **运行期（未绑定）** | `schema_vector` 物理目录，直到该 DS 完成第一次 wiki 编译 | 把未绑定当成「wiki 失败降级」长期混跑 |

统一方案 **P6 拆成两条**，不可再写成一句：

- **P6a 业务召回可降级**：concept/caliber/rule/散文召回失败 = 少一段 `<business_knowledge>`；主链路仍跑，正确性靠 plan_gate / 硬校验。
- **P6b 绑定语料的 schema 不可降级到 catalog**：已绑定 `wiki_corpus_binding` 时，规划器用的 `schema_text` **只**来自 wiki 表页投影。表页缺失 → `SCHEMA_PAGE_MISSING` 遥测 + **本轮不规划该表**（必要时 `unsupported` / 澄清），并触发编译补页。**禁止**「本轮用 db 直渲」。
- **P9 运行可见性（DS 勾选掩膜）**：全量 wiki 按库编译；每个数据源用当前 `CoreTable.checked` × `CoreField.checked` **请求时投影**。取消勾选（库表仍在）→ `selection_excluded`，不是缺页。勾选变更可逆、不重写 wiki。未确认主张 ≠ 未勾选（见 §2 hop）。

`wiki_recall.py` 对 **未绑定 DS** 走 `schema_vector` 仍然合法——那是「还没有 wiki」，不是「wiki 不够用就拼 catalog」。

## 2. Hop 契约（提取 → 问数 → 复利）

```
L0 基线（仅库即可）
  列全集 + 名称锚 + 枚举值候选
  + 身份束 / 同名 / 相似 / 值域重合 → **一律 proposed**
        ↓ 有源码
L1 源码印证（桥梁 + 实践）
  用 JOIN/.eq()/共写组 **验证** 库候选：通过=confirmed，未验=REVIEW
  文档用词经源码钉到 表.字段；源码没有的文档主张 **回退语义匹配 + REVIEW**
  共写组、场景窗、生命周期、代码 label
        ↓ 无源码但有文档
语义名称匹配 → **默认 REVIEW**，不得当硬锚
        ↓
召回面 publish（不含版本史） / 展示面可另留人读说明
        ↓
Ingest / Lint / Publish
  零信任解析 ground 块；列数 == db-catalog；缺代码证据的窗标「未分窗」不得删列
        ↓
运行时召回
  business：scenario + concept + caliber + rule（大窗，图配额原样）
  physical：table + enum + relation（小窗；plan_gate 缺概念时逐条）
        ↓
DS 勾选掩膜（P9，每请求，可逆）
  允许集 = 当前 DS 已勾选表 × 已勾选字段（再叠列权限）
  表未勾选 → 表页不进 schema；仅锚该表的业务页对本 DS 不可用
  字段未勾选 → 表页仍在，投影丢掉该列（always ⊆ 勾选列）
  跨表页裁剪未勾选端，禁止经未勾选表做图扩展
  用户问到且只依赖 excluded → 澄清范围，不是 SCHEMA_PAGE_MISSING，禁止 catalog
        ↓
主张置信过滤
  confirmed → 硬路径
  proposed → 召回但禁止硬 JOIN / 唯一锚
  disputed → 召回为争议；问题依赖则澄清，禁止静默选边
  rejected → 不进召回面
  字段已被掩膜排除 → 其上的争议本轮不问
        ↓
Schema 投影（绑定语料）
  锚点闭包抽物理表 ∩ 勾选表
  → WikiSchemaRenderer 全量缓存（含 group/scenes，不进 prompt）
  → project_schema：always ∪ 本轮命中 scenarios/* 窗 ∪ 口径/证据列 ∪ 问题点名列 ∪ JOIN 端点
    **再 ∩ 勾选字段**
  无场景命中且无点名列：不要把 100+ 列整表塞进 prompt（可只投 always + 点名/JOIN）
        ↓
plan_gate → SQL 执行
  引用表 ⊆ 闭包 ∩ 勾选表；列 ⊆ 勾选字段；硬门禁不靠散文；disputed 不得当唯一谓词
        ↓
复利
  澄清结论 / 高置信成功 SQL → 候选 → REVIEW → published pattern/query
```

提取内部的证据层、编译阶段、角色与出门物以 [`Wiki知识提取规范指南-v1.md`](Wiki知识提取规范指南-v1.md) **§3** 为准。本文件管编译产物如何被召回/投影/门禁消费。

目录 markdown 只做 **导入源 / git-ops 备份**。运行权威在 `wiki_page`。`KNOWLEDGE_WIKI_PAGES_DIRS` 未确认前保持 v1，v3 是预览语料。

### 2.1 三层投影（禁止混成一个开关）

Wiki 表页永远是 **编译期列全集**。运行时叠三层透镜，都不改页文件：

| 层 | 随什么变 | 作用 | 不是 |
|---|---|---|---|
| 主张 `confidence` | 提取 / REVIEW | 硬用 / 软候选 / 澄清 / 不召回 | 不是整页上下线 |
| DS `checked` | 数据源勾选（可逆） | 本 DS 允许的表×字段 | 不是缺 wiki 页；不是二次编译 |
| 场景窗 `group/scenes` | 本轮问题命中 | prompt 里带哪些列 | 不是从 wiki 删列 |

顺序：召回 published → ∩ 勾选允许集 → 争议/未确认打标 → 场景窗裁剪 prompt → plan_gate。`always` ⊆ 勾选列。列权限在勾选之后，不代替勾选。

## 3. 场景是第一类召回对象

- `page-plan.yaml` 的 topic = **提取批次**，不是运行时场景。
- 运行时场景 = 独立 `type: scenario` 页 + `ground:scenario`（hub + window + shared + lifecycle）。spec-v0 原「纯组织页、无 ground」作废。
- 同一张表可属于多个场景；表页 `scenes:` 与字段 `scenes:` / `group: always` 必须和场景 `window` 对得上。
- 未分窗列 **留在表页**，等 mapper/service 证据再划。问到列名时 `project_schema` 展开，不从 wiki 删除。
- 场景无关必留列（列存在则表页必有，引用该表的窗默认带上）：`id`、`enable`、`create_time`、`update_time` 及同族审计列；`code` 有则必留。租户列留表页，**不作 JOIN 端点**。

## 4. 页面类型怎么进规划器

| 类型 | 规划器用法 | 禁止 |
|---|---|---|
| table | schema 权威；列全集；窗裁剪 | 运行时 catalog 补列；按包名切表 |
| enum | 值 + 代码 label；lifecycle 列链 process | 分类字典上假 From→To；编 label |
| scenario | 钉主档 + 投影窗 | 把 Java 包当场景 |
| concept | 说法桥，必须有物理锚 | 无锚术语进规划 |
| caliber | 可执行 predicate + field_targets | 一枚举值一页除非反复被问的命名集合 |
| rule | 条件/后果，可进约束 | 无字段治理口号 |
| process | 钉同一列的真实 From→To | 生成黑话写进正文 |
| relation | EQUI_JOIN 才教 JOIN | 拷贝/快照当 JOIN |
| pattern/query | few-shot 复利 | 未过 lint 的 SQL 进 published |

## 5. 语料三版：取什么、丢什么

| | v1 `wiki-pages/` | v2 `wiki-pages-v2/` | v3 `wiki-pages-v3/` |
|---|---|---|---|
| 角色 | **当前运行时** | 冻结，lint 不通过 | **预览**，组织正确，未切流 |
| 取 | 列相对全；可跑通召回 | 部分口径/枚举补丁 | 场景 hub；label 跟代码；列全集 + 场景划分；正文只写问数事实 |
| 丢 | 弱场景；部分 label/边界错 | 口径/规则过碎；假 process；坏链 | 窗证据仍偏手划（未分窗待 mapper 回填）；未切流 |

切流门槛（同时满足才改 `KNOWLEDGE_WIKI_PAGES_DIRS`）：

1. 绑定语料路径下 **禁止** `WikiSchemaRenderer` catalog 直渲（本契约 P6b 落地）。
2. 金标：表召回@k / 值命中 / 澄清质量 ≥ 现 v1。
3. 场景窗有代码证据的覆盖率可测（未分窗允许存在，但不得伪装成已分完）。

## 6. 与代码的已知裂缝（P0，切流前必须修）

| 位置 | 现状 | 目标 |
|---|---|---|
| `wiki_schema.py` `SCHEMA_PAGE_MISSING` | 缺表页 → `_render_db_table` | 绑定语料：不渲该表 + 遥测 + 补页任务 |
| `wiki_recall.py` | 未绑定 → `schema_vector`（合法）；绑定失败路径易被理解成「永远可以 catalog」 | 文档与分支条件写死：仅 unbound |
| spec-v0 `ground:table.fields` | 「只声明有业务语义的字段；其余留 catalog」 | **列全集**；catalog 只做 lint 对照 |
| spec-v0 `scenarios/` | 「无 ground、纯组织页」 | 必有 `ground:scenario` |
| 召回 → `project_schema` | 已能按 `group`/`scenes` 裁剪 | 必须把本轮 `scenarios/*` 命中写入 `present_pages` / 等价集合，否则窗裁剪不生效 |
| DS 勾选掩膜 | `schema_vector` / catalog 路径认 `checked`；**wiki 召回未按表/字段勾选过滤** | 召回、图扩展、`project_schema`、plan_gate 共用同一允许集；勾选变更可逆不重编译 |
| 主张置信 | relation 仅有 `proposed/confirmed`；枚举值无争议面 | 页内 `confidence`；disputed 进召回面并走澄清，禁止静默选边 |

本文件 **不**改运行时切流，也 **不**改 v1/v2 语料。实现 P6b 与 spec 对齐后再议切 v3。
