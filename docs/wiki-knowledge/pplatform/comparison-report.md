# 源码直提 vs 旧版提取 比对报告（P1-B 验收）

> 日期：2026-08-30 · 底稿：pplatform-web 源码（扫描器五件套，确定性提取）· 对比基线：system-knowledge-v11
> 产物：`docs/wiki-knowledge/pplatform/substrate-pages/`（**175 页**：74 表 + 101 枚举，硬错误 0）

## 一、结论

**源码直提验证通过，且当场抓获了一处语义错误——159 病例的最终真相。**

源码 `CustBuildTypeConstant` 注释为权威：

```java
/** 客户录入 */  public final static String PC_BUILD = "PC_BUILD";
/** 平台录入 */  public final static String AGW_BUILD = "AGW_BUILD";
```

**159/448 澄清卡把 PC_BUILD 标注为"平台录入"是模型推断错误**（从字段名 PC≈平台 臆测），
旧产物未声明 cust_build_type 枚举、无知识背书，错误语义静默传导给用户——这就是
448（54 行）与 449（1000 行）两次统计分歧的完整解释：两次过滤了**不同的字段和不同的值**。
我们自己的演示语料也从澄清卡复制了这个错误（PC_BUILD: 平台录入），本次源码直提当场
纠正。**这是"源码权威 > 产物继承"（D7 权威序）最有力的实证。**

## 三、过程发现与修复（都是真资产）

**扫描器缺口（3 处，已补进技能脚本）**：
1. `*Constant.java` 常量类不扫描 → 新增常量类提取（+17 枚举 106 值）；
2. interface 形态常量（无修饰符字段）漏抓 → 修饰符放宽；
3. 类级 Javadoc 污染字段注释 → tempered 匹配。

**语义错误（1 处，已用源码真值修正全部语料）**：
- `examples/cust_build_type.md`、`examples/identify_style.md`、概念页 `平台录入`：
  PC_BUILD label 改为"客户录入"、AGW_BUILD="平台录入"、INVITE="邀请认证-客户录入"、
  INVITE_AGW="邀请认证-内管录入"（全部以源码注释为准），并加注 159 病例警示。

**召回引擎缺陷（3 处，真实语料暴露，已修 + 测试锁定）**：
1. exact 通道 bigram 污染（共享一个双字即同分平票）→ exact 只用原始连续 CJK 串；
2. 表页字段注释词汇广造成 coverage 结构性偏置 → **IDF 加权覆盖**；
3. RRF 排名融合稀释稀疏强信号（值 label 精确命中被 74 项通道淹没）→ **别名/值标签
   页级分数加成**（"值⊂文本"哲学的页面版，无需分词）。

## 四、验证终态

- 159 原问题在源码直提语料上：`cust_build_type` 权威页**排名第一**，
  passage 内含 `AGW_BUILD=平台录入 / PC_BUILD=客户录入`（正确语义直达规划器）；
- 全量回归 **611 通过**（wiki 契约 11 + P1 试点 8 + 其余 590+）；
- 诚实边界：字段级类型对账需连接真实 DB（当前以 Java 类型族映射）；语义层
  （口径/状态机/术语桥）仍需 LLM 摄取——扫描器给"什么存在"，LLM 给"意味着什么"。

## 五、对架构的最终确认

**扫描器与 LLM 是互补层，不是竞争层**：扫描器给全量覆盖与真值锚点（74 表/106 枚举/
零幻觉），LLM 给语义穿透（13 值状态机/业务口径——扫描器不可达）。Spec B 的
"确定性打底 + 语义跃迁 + 发布对账"三层架构经源码实证成立。旧产物（v11）降级为
"上一轮 LLM 提取的快照"，其语义资产经对账后并入新语料，表示与维护全面切换 wiki。

## 十、向量化存储与召回 V2（追加）

> 2026-09-01 · V1（P2）= 全局指纹单 blob 缓存（23MB/232 页旧语料）+ 每请求重建 index + chunk 级排名进 RRF；
> V2 = per-page revision 增量 + 索引随 store 生命周期缓存 + 原子写/进程锁/熔断 + 页级 RRF 带通道权重 + 超采。

### 10.1 嵌入层（embeddings.py 重写）

| 机制 | V1 | V2 |
|---|---|---|
| 失效粒度 | 全局指纹（页数+chunk数+字符数），同长度编辑不失效 | per-page revision = sha256(页面全文+model+dim)，内容任何变化必失效 |
| 增量 | 任何页变化 → 整库重嵌（3504 chunk/111 次远程调用） | revision 命中即跳过，单页编辑 = 1 页重嵌 |
| 缓存 | 单 blob 写进 git 语料区、非原子、无锁 | `embeddings-cache/embeddings-{model}-{dim}.json`，temp+rename 原子写 + 进程锁双检 |
| 失败恢复 | 每请求全库重试 | 60s 进程级冷却（与 EmbeddingModelCache 熔断同模式） |
| 实测 | — | 全量构建 550s（3504 chunk/104MB 缓存）；二次加载 0.99s 零远程调用 |

### 10.2 召回融合（recall.py）

- **页级 RRF**：向量通道 chunk 超采（top_k×3，≥30）→ 页面聚合 → 页级排名进 RRF（对齐 search.rs），替代 V1 的 chunk 级排名稀释；
- **通道权重**：`LEXICAL_WEIGHT=1.0 / VECTOR_WEIGHT=1.2`（模块常量）；
- **source 三态**：`lexical|vector|graph`——vector 按**边际贡献**判定（词法-only 窗口外的页 = 向量带进来的），遥测可区分通道贡献；
- `wiki_physical_text`（plan_gate 反弹）接入同一 index（复用，无新增构建）。

### 10.3 评测（64 题，严格物理键口径）

| 配置 | 命中率 |
|---|---|
| 纯词法（词法-only 窗口） | 44% |
| 词法+向量（V2，边际贡献 476 处 passage 标 vector） | 44% |

**结论（诚实边界）**：当前 64 题集上向量通道的净命中增量为 **+1 题（"已签约的企业"由向量带入）**——语义页（caliber/rule）密度高导致词法通道已覆盖绝大多数主题，向量的边际价值集中在词法零命中场景（错别字/罕见表述）。`pplatform:*` 旧键体系造成的 44% 天花板问题不变（§九）。向量通道的价值主张调整：**多进程安全、增量成本、physical 通道补强**是本次落地的实际收益；命中率提升预期顺延到题集重标注后（P3.5）。

### 10.4 过程修复

1. source 标注过宽（向量可见即标 vector，476 处失真）→ 改为边际贡献口径（词法-only 窗口对比）；
2. 20 页 P1.5 残留点号 page_key（`caliber.XXX`）确定性重写为 title 派生 slug——store/嵌入/lint 三面统一。
