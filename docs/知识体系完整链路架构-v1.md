# 知识体系完整链路架构（提取 → 管理 → 存储 → 召回）

> 面向人的全景梳理。所有结论以当前代码为准（`backend/apps/knowledge/`），权威依据是
> `docs/统一语义知识体系架构-v1.md`。本文只做结构化梳理与审核，不引入新设计。

## 1. 一句话定位

知识体系回答一件事：**用户说一个业务词，系统一次拿回「概念 + 状态 + 表字段 + 关系 + 口径 + 查法」，
并保证这些内容经过验证、可追责、可召回。** 它的最小可发布、可召回、可进 Prompt 的细胞是
**场景单元（KnowledgeUnitEntry）**，不是单条术语、规则或示例。

---

## 2. 完整链路总览

```text
┌─────────────────────────── 离线（提取侧，不入库） ───────────────────────────┐
│  业务文档 / 代码 / DDL / 只读库画像                                            │
│        │ 两遍提取：先建业务索引，再 Controller→Service→MyBatis→DB 闭环         │
│        ▼                                                                      │
│  manifest(knowledge-package.yaml) + units/*.yaml + coverage.yaml              │
│        │ scan（结构校验 + QA 自检）                                            │
└────────┼─────────────────────────────────────────────────────────────────────┘
         ▼  submit（唯一导入物 = KnowledgePackageV2 语义契约）
┌─────────────────────────── 在线（服务端，入库） ───────────────────────────────┐
│  L1 登记      register_package        → package / evidence / unit / revision  │
│  L2 绑定校验  bind_and_validate        → binding + 字段/查询/关系校验           │
│  L3 审核发布  transition + publish     → revision 状态 + ACTIVE 指针 + K3 术语  │
│  L4 问数编译  compile_business_data_bundle → BusinessDataBundle               │
│        │                                                                      │
│        ▼                                                                      │
│  Query Agent 只读：Bundle 语义槽位 + schema + 字典 entity_bindings             │
└──────────────────────────────────────────────────────────────────────────────┘
```

四段各司其职，中间不跨越：

| 段 | 做什么 | 谁来做 | 产出 |
|---|---|---|---|
| 提取 | 把业务系统变成场景单元包 | 离线（人 + 提取器） | manifest + units + coverage |
| 管理 | 登记、绑定校验、审核、发布 | 服务端 API | 可召回单元 + 绑定/部署状态 |
| 存储 | 一份可编辑真相 + 几种定位索引 | DB（6 张 2.0 表） | `knowledge_unit_revision.content` |
| 召回 | 按问题定位 1~2 个单元并裁剪进 Prompt | 服务端编译 | BusinessDataBundle + entity_bindings |

## 3. 模块分层（代码）

```text
apps/knowledge/
├── semantic/          ★ 2.0 核心（唯一语义契约 + 生命周期）
│   ├── schema.py      契约 KnowledgePackageV2 + 引用闭包校验（extra=forbid）
│   ├── scanner.py     装配：manifest + units/*.yaml → KnowledgePackageV2
│   ├── lint.py        离线 QA：覆盖矩阵 + 质量信号（review aid，非运行时门禁）
│   ├── service.py     register / bind_and_validate / transition / publish
│   └── api.py         HTTP 路由（/knowledge/packages …）
├── compile/           ★ 运行时召回
│   ├── bundle.py      BusinessDataBundle（Query Agent 的唯一业务知识输入）
│   └── compile.py     compile_business_data_bundle + knowledge_prompt_payload
├── reuse.py           VQR 短路复用（只复用 certified 范例）
├── providers.py       召回 Provider 协议 + DictionaryProvider
├── dictionary_recall.py  字典召回（术语→实体）
├── policy.py          召回策略（复用开关/相似度阈值/预算）
├── scope.py           召回结果的行列权限过滤
├── models.py          KnowledgeMatch / FieldTarget / KnowledgeBundle
├── capture/ staging/ linkage/ lineage/ assets/   ★ 1.0/沉淀辅助平面（停写保留读）
└── db_models.py       13 张表的 SQLModel 定义
```

调用侧（`apps/chat/`）只依赖两个入口：

- `steps/knowledge.py::match_knowledge` —— 编译 Bundle，写 `llm_service.compiled_knowledge`
- `binding_resolver.py::resolve_entity_bindings` —— 术语→字段实体绑定

分层原则：**契约（schema）与装配（scanner）分开，离线 QA（lint）与运行时校验（bind）分开，
沉淀平面（capture/staging）与正式平面（semantic）分开。**

## 4. 存储模型（13 张表）

### 4.1 2.0 正式平面（6 张，语义契约的唯一落点）

| 表 | 模型 | 职责 | 关键字段 |
|---|---|---|---|
| `knowledge_package` | SemanticKnowledgePackage | 包的不可变合订本（证据 + 内容快照） | package_id, revision, content_hash, source_document |
| `knowledge_source_evidence` | KnowledgeSourceEvidence | 证据条目（来源 + locator + hash） | evidence_key, source_id, evidence_kind, locator |
| `knowledge_unit` | KnowledgeUnit | 单元指针，不含内容 | unit_key, domain, active_revision_id |
| `knowledge_unit_revision` | KnowledgeUnitRevision | **唯一可编辑真相** = content(KnowledgeUnitEntry) | content(JSONB), revision, lifecycle_status, validation_status |
| `knowledge_binding` | KnowledgeBinding | 单元 ↔ 数据源绑定 | datasource_id, mapping(字段指纹/关系/已验证查询), status(UNBOUND/BOUND/STALE) |
| `knowledge_deployment` | KnowledgeDeployment | 发布指针 | revision_id, status(BUILDING/ACTIVE/ERROR/RETIRED) |

### 4.2 1.0 / 沉淀辅助平面（7 张，停写保留读）

`knowledge_asset`（K1~K5 运行时投影）、`knowledge_schema_ref`、`knowledge_evidence`、
`knowledge_episode`（对话片段）、`knowledge_staging`（待审沉淀）、`knowledge_lineage_event`、
`knowledge_capture_job`（抓取任务）。

> 架构决策：**发布后只写 K3 术语（带 `unit_revision_id`）作定位索引**，K1/K2/K4/K5 停写新行；
> 这些辅助表用于对话沉淀与回溯，不进入 Query Agent 的正式召回通道。

### 4.3 两份真相，一种索引

- **可编辑真相只有一处**：`knowledge_unit_revision.content`。
- **运行时索引**：`knowledge_unit.active_revision_id` + `knowledge_deployment(ACTIVE)` + K3 术语定位。
- 包无生命周期（只留最近一次包级诊断）；**单元**才有四态。

## 5. 数据流转细节

### 5.1 提取（离线，L0）

```
文档 → 业务索引（域地图/场景目录，不入库）→ 代码/DB 闭环 → 场景单元包
```

- **权威顺序**：库字段实际值 > 代码读写 > 文档主张 > skill 导航（文档不赢代码，冲突标 `conflicts`）。
- **单元必须回答**：概念/别名 → 对象粒度 → 流程状态/data_effects → 表字段字典 → proposed 关系
  → 口径/规则 → proposed 查询范式 → 证据。**缺「绑到真实字段」不算完成。**
- **磁盘形态**：manifest（`sources`/`evidence` 只写一次）+ `units/<unit_id>.yaml`（一个单元一个文件）。
  `units` 是传输字段，组装前移除；单文件内联 `knowledge_units` 是退化形态，同一条组装逻辑。
- **QA 自检**：`coverage.yaml` 穷举全量物理表，`COVERAGE_GAP` 是离线验收阻断项（全系统无遗漏），
  其余（METRIC_MISSING / PROCESS_NOT_SERIALIZED / RELATION_UNJUSTIFIED / FAKE_EXECUTED / DOC_UNDERUSED）是 advisory。

### 5.2 登记（L1）

`POST /knowledge/packages`（或 upload）→ scanner 装配 → `KnowledgePackageV2` 校验 →
`register_package` 幂等写入 package/evidence/unit/revision（DRAFT）。同 `package_id + revision`
内容变了必须递增 revision。

### 5.3 绑定校验（L2）

`bind_and_validate(datasource)`：
1. 字段存在 / 类型对照 Catalog；
2. 查询范式只读执行（`passed:true` 才写入 `binding.mapping.verified_query_patterns`）；
3. 关系两端字段存在；`proposed` 关系 → WARNING；
4. 缺表缺字段 → FAIL，但 binding 仍落 `BOUND`（不蒸发）。

### 5.4 审核发布（L3）

`transition_revision`（DRAFT → IN_REVIEW → APPROVED）→ `publish_revision`：
原子切换 ACTIVE 指针 + 只写 K3 术语（带 `unit_revision_id`）。发布失败不切指针。

### 5.5 运行时召回（L4）

```
问题 → 精确标题/别名/概念 ⊂ 问题 → K3 unit_revision_id → 排序(精确命中数, K3 分, unit_key)
     → 最多 2 个 ACTIVE 单元 → 按问题裁剪 → BusinessDataBundle
     → knowledge_prompt_payload（语义槽位）+ entity_bindings（术语→字段）
```

- **裁剪**：必带命中相关 datasets/fields/relationships；口径/规则按词相交；状态词才带 process；
  verified 查询最多 2 条。预算截断先丢 process/证据，后丢口径/字段。
- **无命中**则 Bundle 无单元，只靠 schema，**禁止灌全部已发布单元**。
- **双通道**：Bundle 语义槽位（datasets/fields/relationships/calibers/metrics/rules/verified_examples）
  + 字典 entity_bindings（NL 短语 → 规范维度值 + 物理字段）。二者不合并，靠 `table.field` 名对应。
- **VQR 复用**：仅 `stage=generate` 且存在 `certified`（bind 时执行通过）范例时尝试短路；
  命中要求相似度超阈值 + 每个 SQL 字面量都在问题里逐字出现（否则回退 LLM 生成）。

## 6. 关键设计决策（审核通过的约束）

| # | 决策 | 理由 |
|---|---|---|
| 1 | `KnowledgePackageV2` 是唯一语义契约 | 杜绝第二套 schema 漂移；`extra=forbid` 兜底 |
| 2 | 单元是唯一可发布/召回/进 Prompt 的细胞 | 审核看得到场景，问数一次拿全定义+状态+表+口径 |
| 3 | 关系默认 `proposed`，绑定才 `confirmed` | 不伪造验证；`FAKE_EXECUTED` 规则兜底 |
| 4 | 跨场景最多召回 2 单元，靠共享表名拼接 | 不建单元关系图（明确不做图数据库） |
| 5 | coverage/lint 是离线验收，不是运行时门禁 | 离线 QA 与运行时校验（bind）职责正交 |
| 6 | VQR 只复用 `certified`（执行验证）范例 | 短路跳过 LLM 校验，必须最高信任门槛 |
| 7 | 权威顺序：库值 > 代码 > 文档 > skill | 文档不赢代码，冲突显式标出 |
| 8 | 发布只写 K3 术语索引，K1~K5 停写 | 一份可编辑真相 + 一种定位索引 |

---

## 7. 审核结论与遗留

**审核通过**：链条完整、模块分层清晰、无补丁式修改、无过度设计。端到端验证（22 单元 / 74 表 /
0 缺口 / 46 测试通过 / lint 0 阻断 0 提示）。

**遗留（低优先，不阻塞）**：
1. `knowledge_package.status` 列（默认 `REGISTERED` 永不流转，`!= RETIRED` 过滤是死逻辑）——需 migration；
2. `PROCESS_NOT_SERIALIZED` 只抓「零串联」，不抓「部分串联」——当前数据无此问题，规则已如实说明局限；
3. units/ 目录有但 manifest 未列出的孤儿文件会被静默忽略（显式清单设计使然）。

**明确不做**：1.0 兼容导入、自动升格、图数据库、通用 SQL 编译器、单元向量新索引、
语义归并服务、产品内提取器、Query Agent 内再知识规划、为修闭环加新表。
