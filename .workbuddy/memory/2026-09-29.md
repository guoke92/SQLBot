## 工具体系"状态归属"专项分析

承接上条，专门分析工具层的"无状态"问题，产出 `docs/reviews/tool-state-ownership-analysis-2026-09-29.md`。

**核心诊断**：不是"工具无状态"，而是"状态没有归属"——同一批状态同时存在于 4 个介质（闭包 / 进程内全局 `runtime_context._contexts[run_id]` / LangGraph 检查点 / DB `result_dataset`），三者无划分规则、无单一真值源、无恢复协议。

**已核实的关键事实（后续可复用）**
- 工具是**闭包**（`registry.py:413` `build_agent_tools(llm_service, access_scope)`），不是纯函数。
- "本轮交付的 SQL 是哪条"被独立推导 **6 次**：`_agent_has_sql_result` / `has_publishable_query_result` / `complete_answer._sql_already_delivered` / `turn_fold._baseline_sql` / `agent_finalize`(result_dataset) / `memory_slots.active_baseline_sql`。
- `memory_slots.active_baseline_sql` **写了没人读**：唯一读取方法 `extract_change_baseline()` 零调用；`build_agent_system_prompt(memory_slots=..., change_baseline=...)` 标 `# noqa: ARG001`（`agent_prompt.py:158-159`）；`render_memory_slots` docstring 明说 "no longer injected into System"。上一轮 SQL 只能靠 `fold_turn`（`turn_fold.py:111-129`）排版成字符串塞回历史。
- `get_table_schema` 有 4 处副作用：读全局袋 `load_plane()` / 写全局袋 `save_plane()`（`catalog_tools.py:145-157`）/ 写 `chat_question.db_schema`（:426）/ 返回 `data.schema_text`。`chat_question.db_schema` 的读点全在已退役 `nlq/` 里 → "写了没人读"第三例。
- `sql_delivered` 是唯一只存进程内全局袋、**无 state 镜像**的控制标志；`_hydrate_chat`（`runtime_context.py:169-176`）只回填 4 个 key（llm_service/access_scope/llm/bound_tools），`sql_delivered` 无兜底。
- `_consume_probe_budget`（`execute_sql.py:96-99`）是无锁 read-modify-write，串行下无害，一上并发即丢更新。
- 控制面信号塞在 `data` 里：`interrupt_required` 决定图路由（`unified_agent.py:697-701`）、`skipped` 决定预算计数、`required` 决定交付/探查。`_GENERIC_SKIP_KEYS`（`tooling.py:413-424`）是控制面 key 的黑名单 —— 需要黑名单即证明两平面混在一起。
- `runtime_context.py:100-108` 的注释说明了原始取舍（checkpoint 不放 ORM 对象、权限重算），这个取舍是对的；错在把**可序列化的业务状态**也一起放外面了。分界线应是"能否 msgpack 序列化"。

**建议路线**：路线 B（数据面引用化，`sql_ref` 句柄）先落一片 → 消掉 token 双付、SQL 漂移、无 memo；路线 A（控制面显式化为 `TurnContext`）跟上。落地顺序见文档第六节（第 1 步约 1 小时：`sql_delivered` 改为从 `tool_steps` 派生）。

## 上下文/工具/Loop 重构方案

承接上条，参照 Claude Code / Agent SDK、Manus（Peak Ji 六原则）、多轮 NL2SQL 生产实践，产出完整重构方案 `docs/reviews/context-tools-loop-refactor-2026-09-29.md`。

**参照系六条判据**（用于给任何 agent 上下文设计打分）：J1 状态外部化 / J2 引用化 / J3 压缩可还原 / J4 预算显式 / J5 recitation / J6 决策单点。本项目六条里五条不及格。

**本轮新核实的事实（上下文层）**
- 折叠是**读时投影**：`build_continued_messages`（`session_transcript.py:143-171`）每轮把历史全量读出再 `fold_history`（`turn_fold.py:69-108`）重新折；折叠结果不回写 → O(n²) 读放大，`Chat.agent_transcript` 只增不减（`session_transcript.py:72-96`）。
- 折叠有硬缺口：`protect_from = len(turns) - keep`（`turn_fold.py:83`）最近 3 轮永不折叠；往返折到 L2 仍超预算则 `break`（`:105`）**静默超限，无降级路径**。token 估算 = `字符数/4`（`:27-37`），无真实 tokenizer。
- **存在两条并行通道且用的是差的那条**：① `ChatRecord.answer.datasets[].sql`（`context.py:757`，**截断 1200 字符**）→ `referenced_turns`（`:842-873`）→ `memory_slots.active_baseline_sql`（`memory_slots.py:97-109`，**已水合**）→ 被 `# noqa: ARG001` 摘掉；② ToolMessage → `_baseline_sql` 猜（`turn_fold.py:162-178`）→ 排版成 `SQL：` 明文 → 模型再解析回来。通道 ① 的数据被截到 1200 字符，通道 ② 是全文 —— 两者已不一致。
- `fold_turn` 用正则从消息里猜三件事：基准 SQL、用到的 schema 字段（`_schema_field_map` + `_sql_usage`，依赖 sqlglot）、知识 page_keys。全部可以改从 state/DB 直接读。删除量约 130 行（`turn_fold.py:162-288`）。
- `agent_transcript["folds"]` **写了没人读**（`session_transcript.py:124-140` 写，`:58` 只读 messages）→ 折叠每轮重新决策，前缀不稳定，KV-cache 被自己打掉。

**本轮新核实的事实（Loop 层）**
- 预算只有 1/6 维度有真上限：执行轮 5；**知识轮无上限**（`UNCOUNTED_TOOLS`，`agent_knowledge.py:35`）、**总工具调用数无上限**（`tooling.py:672` 循环无计数）、**澄清次数无上限**（`agent_clarify.py:169-171` 每次重置 `tool_rounds=0`）、探查是软预算永不阻断、上下文 token 不计数。
- 澄清清空 `tool_steps` 但 `messages` 里的 ToolMessage 原样保留 → 同一轮内两份互相矛盾的证据（`_agent_has_sql_result` 说没交付、模型看到交付过）。
- 停止条件只有：非可重试失败、同一失败签名连犯 2 次（`tooling.py:833-845`）、`rounds >= round_limit`（`unified_agent.py:426`）。

**方案骨架**：原则 1 上下文是投影不是累积物；原则 2 输入用句柄（`sql_ref`）、输出分平面（`signals`+`payload`）；原则 3 终止条件可枚举。新增 `apps/chat/context_spec.py`（六段：rules / catalog_outline / recap / working_set / sql_workspace / turn_brief）、`apps/chat/tools/contract.py`（`ToolOutcome[P]` + `Signals`）、`SqlWorkspace`（`SqlRevision` rev 链）、`compute_verdict` 单点。四期落地：Phase 0 只观测 → Phase 1 消 P0（signals/verdict/预算单点）→ Phase 2 上下文重构（sql_ref + recap 读记录 + turn_brief）→ Phase 3 轮内清除与并行。

**待用户拍板**：D1 SQL workspace 承载（建议只放 AgentState，交付时随答案落库）／D2 `active_baseline_sql` 接回还是删除（建议接回）／D3 是否接受有状态工具（建议保持纯函数 + refs）／D4 转录本裁剪策略／D5 预算缺省值需实测校准／D6 `chat_question.db_schema` 建议删。
